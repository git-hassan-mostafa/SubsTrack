# Non-Obvious Patterns & Gotchas

> Read the relevant entries BEFORE editing code in that area. Referenced from `CLAUDE.md`.
> Area index: payments → 1,2,6,7,12,13,14,15,21,22,34,49 · **pay oldest month first → 77** · **multiline inputs / scroll → 78** · **customer-list status badges → 56,56b** · service lines / multiple plans → 1,16,25,41,49 · currency → 18,19,21,22,24,36,38 · branches → 26,27,28,29,30,31,32 · tiers → (see docs/features.md) · sales/products → 35,36,37,50 · product stock → 48 · dashboard revenue / debts → 50 · auth/signup → 3,4,33,40 · i18n/UI → 5,11,17,39,44,45,46,47 · cross-slice → 9 · offline mirror writes → 48,49 · **performance / render cost → 51,52** · releases / OTA → 53 · **sheets / forms closing (unsaved changes) → 54,55** · **audit trail → 57,58,59,60,61,62,63,64,65,66,67,71,72,73,75,76** · **whatsapp invoices → 68,69,70,80** · **branch filtering vs RLS → 73** · **debt dates / history grouping → 74** · **customer history / audit subject_id → 75**.

1. **Payments use upsert** — the `UNIQUE(customer_plan_id, billing_month)` constraint (per **service line**, not per customer) means re-paying a voided month upserts the existing row (nullifies `voided_at`), not inserts a new one. A customer with several lines can hold one payment per line per month; the upsert `onConflict` target is `customer_plan_id,billing_month`.

2. **Payment amount is a snapshot** — stored at recording time, never recomputed from `plan.price`. Historical amounts survive plan changes or deletions.

3. **`superadmin` role exists in DB but is not exposed in SubsTrack** — it appears in `UserRole` type but is filtered from the user management UI. Only the SuperAdmin app uses it.

4. **Login email is synthetic** — `username@tenantcode.com` is a convention for unique identification in Supabase Auth, not a real email.

5. **Language change reloads the app** — Arabic requires RTL layout via `I18nManager`, which needs a reload. This is handled in `storage.ts`.

6. **In-flight guard for double-tap** — stores check `if (get().loadingCreate) return` before proceeding to prevent duplicate payment submissions.

7. **Year-scoped payment loading** — `paymentStore` fetches payments only for the displayed year. Navigating years triggers new fetches (cached by year).

8. **`before_start` is a 4th month status** — months before **`line.startDate`** (the `customer_plans` row's own start; `customers` has no `start_date`) are non-tappable and shown gray regardless of other logic.

9. **No cross-slice imports at module scope** — slice files may import types from peer slices but never the slice creator or per-slice hook. Cross-slice reads happen inside actions via `get().<otherSlice>`. Caller-supplied data (tier, usage, currency) still flows in as parameters from the component.

10. **SuperAdmin uses service role key** — `supabaseAdmin.ts` bypasses RLS entirely, giving full DB access. This is intentional for the SaaS owner's admin operations.

11. **Cairo font for Arabic** — loaded via `expo-font` at root layout; `useAppFont` hook applies it. The custom `Text` component selects font family per current language.

12. **`billing_month` is always YYYY-MM-01** — the first day of the month, always. Validated in PaymentService before insert.

13. **Multi-month payments store the bundle price, not per-month** — `payment.amount` is the total bundle price. The `durationMonths` field on the payment record tells the grid how many consecutive months are covered from `billingMonth` forward.

14. **`isGroupSecondary` flag in MonthEntry** — months 2+ in a multi-month payment block have `isGroupSecondary = true`. The grid uses this for visual merging (no gap between cells, "Included" sublabel) and to prevent double-tapping secondary months.

15. **Multi-month conflict resolution** — `createMultiMonthPayment` shifts `effectiveStart` and reduces `effectiveDuration` when leading months are already paid. The recorded payment starts at the first uncovered month, not the requested start, and covers only the remaining months in the original block.

16. **Non-regular customers never appear in unpaid counts** — dashboard `unpaidThisMonth` and the "Unpaid" tab filter only query regular (`is_regular = true`) active customers. Non-regular customers can still have payments recorded normally. With **multiple plans per customer**, these counts are aggregated across a customer's **active service lines**: `unpaidThisMonth` counts a customer once if any active line is uncovered this month (`CustomerRepository.countUnpaidForMonth` joins `customer_plans`); the list's fully-paid badge (`PaymentService.buildCustomerStatus`) requires every DUE active line to have a covering payment for green (a partial payment counts as covered — see #34).

17. **EmptyState first-data button** — `EmptyState` accepts an optional `onAction` + `actionLabel` prop. Lists (plans, customers, users) pass these to render a "Create First X" button when the list is empty and the user is not actively searching.

18. **`null currency_id` means USD** — every money column (`plans.price`, `payments.amount_due`/`amount_paid`, `users.display_currency_id`) treats `null` as USD. USD is never inserted as a `currencies` row.

19. **CurrencyInput does NOT convert on currency change** — switching the dropdown from USD to LBP keeps the typed `100` literal, reinterpreting it as `100 LBP`. This is correct because the user is saying "I meant this number in the other unit," not "convert what I typed."

20. **Display currency is a TENANT setting, not a device preference** — it lives in `tenant_settings` under the `DisplayCurrencyId` key and is read only through `useDisplayCurrencyId()` (`src/state/hooks/useTenantSettingSlice.ts`). It used to sit in `uiPrefStore` (AsyncStorage), which meant two staff of the same organization could see different currencies and a reinstall lost the choice. There is still no `display_currency_id` column on `users` or `tenants` — don't add one. Consequences of the move: it is **admin-writable only** (RLS on `tenant_settings`), it **resets on logout** with the rest of the slice and is re-fetched by `primePostAuth`, and an unknown/soft-deleted id falls back to USD through `findCurrency`.

21. **`rate_per_usd_snapshot` freezes payment USD value** — every payment row carries `rate_per_usd_snapshot`, the live `currencies.rate_per_usd` at the moment the payment was recorded. PaymentDetailSheet (receipt), CustomerPaymentPanel year total, and Dashboard aggregates all convert via this frozen rate, so editing a currency's live rate never retroactively shifts historical USD values. USD payments (`currencyId === null`) store snapshot = 1. **Plan prices** still use the live rate (forward-looking pricing — that's the desired behavior). The snapshot is captured at the boundary: `PaymentFormSheet` resolves the `Currency` from `useCurrencyStore` and passes it into `paymentStore.createPayment` / `createMultiMonthPayment`, which extract `currency?.ratePerUsd ?? 1` and forward to `PaymentService`. **Editing** a payment also re-snapshots: `PaymentService.updatePayment(id, amountDue, amountPaid, currency)` recomputes `ratePerUsdSnapshot` from the (possibly newly chosen) currency at edit time, so historical USD totals reflect the corrected record. Use the `paymentSnapshotCurrency(payment, currencies)` helper in `src/core/utils/currency.ts` when displaying a payment — it clones the live `Currency` with `ratePerUsd` overridden by the snapshot.

22. **Dashboard aggregates in USD using snapshots** — `DashboardService.getMetrics()` fetches `{amount, rate_per_usd_snapshot}` rows for the month and divides each by its snapshot before summing. The screen then re-formats the USD total into the tenant's display currency. No live-currencies lookup is needed for the sum — the snapshot is the rate.

23. **`authStore.restoreSession` / `login` prime the currency store** — after auth succeeds, `useCurrencyStore.fetchCurrencies()` is called so all downstream `CurrencyInput`s and formatters have data immediately. `logout` resets the currency store.

24. **`currencies.code` is uppercase A-Z, 2-8 chars, and never 'USD'** — enforced by a CHECK constraint and validated again in `CurrencyService.validate()`.

25. **Quick Pay `?quickPay=1` handshake** — the customer list opens `customers/[id]?quickPay=1` when a customer has no eligible fixed-price line to auto-pay (custom-price / plan-less). `CustomerPaymentPanel` reads the param, waits for the selected line's grid to load, then auto-selects the current-month entry and opens `PaymentFormSheet`. A `useRef` guard fires it once per mount; `router.setParams({ quickPay: undefined })` clears it. **With multiple plans**, the list quick pay (single or bulk) collects **all eligible fixed-price lines** at once via `paymentStore.bulkPayCustomers` (one `BulkPayCustomerRequest` per line, each carrying its `customerPlanId`) — it no longer calls `createPayment` / `createMultiMonthPayment` directly. The per-cell 3-dot menu (Open / Pay / Void) inside the panel still pays the tapped month of the **selected line** via `createPayment` / `createMultiMonthPayment`.

26. **`branch_id NULL` semantics** — on `users` it remains a real selectable state meaning "tenant-wide admin" (form picker is `nullable` only when `role === 'admin'`). On `plans` and `products`, NULL means **SHARED** — a catalog item visible to every branch; tenant-wide admins choose it freely (the `PlanFormSheet` / `ProductFormSheet` branch picker is `nullable={user?.branchId === null}`, and neither `PlanService` nor `ProductService` requires a branch). On `customers`, NULL is a **legacy-only** UNASSIGNED state: the form picker is `nullable={false}` and `CustomerService` rejects `branch_id = null` when the tenant has any active branch — the only way a customer ends up null today is if its branch was deleted (FK `ON DELETE SET NULL`). The header `BranchSelector`'s "Unassigned" filter exists to surface those orphaned customer rows for re-assignment.

27. **Tenant-wide admin = `users.branch_id IS NULL`** — there is no separate role for them. Any admin without a branch is effectively a "super admin" for the tenant. Multiple are allowed. The existing SaaS-level `superadmin` role (separate SuperAdmin app) is unrelated.

28. **Branch filter is purely UI state** — `uiPrefStore.currentBranchId` (persisted to AsyncStorage). RLS lets tenant-wide admins see everything; the app passes `?branch=X` filters per-query to narrow the view. Branch-scoped users ignore `currentBranchId` and always see only their branch (their `users.branch_id` is the only possible filter, enforced by RLS).

29. **`BranchSelector` is a compact chip embedded inside `PageHeader`** — it renders as a small pill (`rounded-full px-3 py-1`, gray when "All Branches" is active, indigo-tinted when filtered) directly under the page subtitle. `PageHeader` always renders `<BranchSelector />` internally — screens never instantiate it themselves. Dashboard has no `PageHeader`, so the chip is placed inside the greeting block (under the date line) in [DashboardScreen.tsx](../SubsTrack/src/modules/dashboard/screens/DashboardScreen.tsx). The chip's tap opens the shared `DropdownModal` exported from [Dropdown.tsx](../SubsTrack/src/shared/components/Dropdown.tsx) — same search/option-list UX as form-field dropdowns. Self-concealment is unchanged: returns `null` for branch-scoped users and for tenants with fewer than 2 active branches. The same "≥2 active branches" gate is exposed as `useIsMultiBranchActive()` in [BranchPicker.tsx](../SubsTrack/src/shared/components/BranchPicker.tsx) and shared with `BranchPicker` so every dropdown / picker / filter hides in lockstep.

30. **New tenants auto-get a "Default Branch"** — [TenantService.createTenant](../SuperAdmin/src/modules/tenants/services/TenantService.ts) inserts a `Default Branch` row right after the tenant row, before the admin auth user is created. `branches.tenant_id` has `ON DELETE CASCADE` so the existing rollback paths still clean up correctly.

31. **Single-branch tenants behave as if branches don't exist** — with exactly 1 active branch, `BranchSelector` + every `BranchPicker` hide. Form sheets auto-bind new records to that lone branch (`CustomerFormSheet`, `PlanFormSheet`, `UserFormSheet` for `role='user'`). `UserFormSheet` toggles `branchId` back to `null` when the role flips to `admin` because admins remain tenant-wide. The auto-fill applies only on _create_, never on edit. The Branches admin CRUD screen stays reachable so admins can add a 2nd branch and activate multi-branch UI.

32. **Branch is mandatory for customers and staff users once any branch exists** — `BranchPicker` is passed `nullable={false}` in `CustomerFormSheet` and (when `role === 'user'`) `UserFormSheet`. Submit buttons are disabled until a branch is picked, and the services re-validate (`CustomerService.validateInput`, `UserService.validateBranchAssignment`) using a `tenantHasBranches` flag that each store reads from `useBranchStore`. **Plans and products are NOT mandatory** — like products, plans can be created SHARED (null branch) by tenant-wide admins, so `PlanFormSheet` / `ProductFormSheet` pass `nullable={user?.branchId === null}` and neither service requires a branch. Tenant-wide admins (`users.role === 'admin'` with `branch_id = null`) are likewise exempt for customers/users. The 0-branch case (legacy tenants with no branches yet) skips enforcement entirely.

33. **Self-service tenant signup goes through an Edge Function, never direct inserts** — the SubsTrack mobile app ships only the anon key, and there is no INSERT policy on `tenants`/`branches`/`tier_plans`. The public [create-tenant](../SubsTrack/supabase/functions/create-tenant/index.ts) edge function (deployed with `--no-verify-jwt`) is the **sole** anon-accessible path for creating a tenant. It uses the service-role key to perform the full sequence with cascading rollback: lookup Free tier id → `tenants(tier_id=Free)` → `branches` ('Default Branch') → `auth.users` → `public.users` (role=`superadmin`, branch_id=null). The pre-check on the organization screen uses `is_tenant_code_available` — a SECURITY DEFINER RPC granted to `anon` that returns a boolean (no row data, just a yes/no oracle). Self-signup mirrors the role assignment SuperAdmin's `TenantService.createTenant` uses (`superadmin`), which means the new owner is filtered from their own Users screen per note #3 — same behavior as tenants created from SuperAdmin today. Future paid-plan gating plugs into this edge function (the `paymentToken` field is already accepted-but-ignored in the request body) and into `subscriptionStore.upgrade()`.

34. **A partial payment reports as `"paid"` — there is NO `"partial"` `MonthStatus`** — when a payment covers a month with `amount_paid > 0` (even if `balance > 0`, i.e. amount_paid < amount_due), `PaymentService.buildMonthGrid` emits `status: "paid"`. The month + customer look settled; the outstanding `balance` is surfaced **only** through the **Debts** tab ("months" category, `balance > 0`) and drill-in views. `MonthStatus` is `"paid" | "unpaid" | "future" | "before_start"` — a partial payment has no distinct cell color/label. The owed amount still rides along on `MonthEntry.balance`, and the drill-ins that need it read `payment.balance` directly (not the status): `PaymentDetailSheet` (amber card + "{amount} added to debts") and the Payments-tab ledger `PaymentListCard` (partial badge), which keeps its transaction-level `PaymentStatusFilter = "all" | "paid" | "partial"` (`balance > 0`). The payment form (`PaymentAmountPaidSection`, shared with `SaleFormSheet`) shows an inline amber notice (`payments.partial_debt_notice`) when the paid amount is below due. **Customer-list badges:** `CustomerStatus.status` (#56) is `"paid"` when every DUE line is covered — a single partially-paid line counts as covered, so a single-plan partial reads fully **paid** (green). `"mixed"` is the multi-plan case (some lines covered, at least one not), rendered as the amber **"N/M plans paid"** badge. `buildCustomerStatus` marks **any covering payment as settled** regardless of balance, and it is the only implementation. Slice mutations (`createPayment`, `createMultiMonthPayment`, `updatePayment`, `voidPayment`) re-run it for that customer via `syncCustomerStatus`. The unpaid tab + Quick Pay gating treat `"paid"` or `"mixed"` as "already has a payment record for this month." A partial payment behaves like a full one everywhere a payment record matters (`PaymentDetailSheet` opens on tap, `MonthGrid` multi-month grouping merges them, `PaymentFormSheet` treats them as multi-month conflicts, `CustomerPaymentPanel`'s `paidCount` includes them). The unpaid banner / unpaid tab only fire for `"unpaid"`. **Overdue is its own pill, not an override:** `CustomerStatus.overdue` is true whenever any active line has an unpaid month *before* this one, and the card shows it **beside** the month pill rather than replacing it (#56) — so "✓ Paid + Overdue" is a real, useful state. It is computed in the same `buildCustomerStatus` pass that produces `status`, from grids built per line across every year from `startDate` to now, so the decision stays inside `buildMonthGrid` (rule #1). `CustomerListScreen` refreshes the whole map via `useFocusEffect` (keyed on `customers`) so paying a past month in the detail panel updates the badge on return. The unpaid tab includes a customer when `status.overdue || status.status === "unpaid" || status.status === "mixed"`. **No grace period (removed on purpose):** the badge's red `"unpaid"` is an *absence* fallback (no payment → red), which only agrees with the grid because the grid also turns a month `"unpaid"` on its first day. `tier_plans.grace_days` and every `graceDays` parameter were deleted (DB column dropped); a future "not late yet" state must change `buildMonthGrid`, the card badge, the Unpaid tab, **and** the dashboard's `unpaidThisMonth` tile (whose collected-% ring would otherwise read 100% while nobody has paid) in one go.

35. **Sales are independent from subscription payments** — `sales` and `payments` are separate tables with separate services, slices, and screens. They share zero code beyond the snapshot rate principle (`rate_per_usd_snapshot`). Don't try to unify them — subscriptions are month-shaped (`billing_month`, `duration_months`, multi-month coverage), one-off sales are not. The only place they intersect is `DashboardService.getMetrics()`, which sums both in USD using each row's frozen snapshot rate and returns `subscriptionRevenue` + `salesRevenue` + their combined `monthlyRevenue`.
    - **A sale is a HEADER (`sales`) + one or more LINES (`sale_items`)** — one sale can hold several products (mirrors `customers` → `customer_plans`). The header owns the one-per-sale facts: **single currency + `rate_per_usd_snapshot`**, the summed **`total_amount`** (now **app-written, NOT a generated column** — a generated column can't sum a child table), `amount_paid` (partial → one "Sales" debt for the whole sale), and a **frozen `items_summary`** text. Everything header-level (debt = one sale, wallet = one cash entry, dashboard totals) is unchanged by multi-product. `sale_items` rows carry `product_id` / `product_name_snapshot` / `quantity` / `unit_amount`; `line_total` is derived in the mapper (no column). **One currency per sale** — the form auto-converts each product's catalog price into the sale currency (`convert()`); lines never carry their own currency. Product soft-vs-hard delete now counts **`sale_items.product_id`** references, not `sales`.
    - **`items_summary` is the search field + the list/debt/wallet label** — a frozen summary of the products (e.g. `"Water ×2, Bread"`) built by `SaleService` at create. `SaleCard` title, `SaleDetailSheet` hero, the Debts "sales" `label`, and the wallet `WalletItem.label` all read `sale.itemsSummary` (was `productNameSnapshot`). Lean reads (`partialSales`, `unremittedForWallet`, dashboard totals) therefore need **no `sale_items` join**; only list/detail join `sale_items(*, products(*))`. The Sales-tab **product filter** resolves "sales containing this product" from `sale_items` (web: sale-ids sub-query → `.in('id', …)`; offline: `EXISTS` subquery) since `product_id` is no longer on the header.

36. **`paymentSnapshotCurrency()` works on any row with `currencyId` + `ratePerUsdSnapshot`** — despite the name, the helper in `src/core/utils/currency.ts` is shape-based, not payment-specific. Reuse it for sales (`SaleCard`, `SaleDetailSheet`) so historical USD-equivalent values stay drift-free when a tenant edits the live `currencies.rate_per_usd`. If you later add another snapshot-bearing entity (refunds, deposits), reuse it again rather than copying the pattern.

37. **`AsyncEntityPicker` replaces `Dropdown` only when the option list is too large to fit in memory** — `Dropdown` does client-side filtering against a pre-loaded options array (perfect for branches, currencies, plans). `AsyncEntityPicker` accepts a `loadPage(search, page)` callback, debounces input via `useDebounce` (300 ms), paginates via `FlatList.onEndReached`, and discards stale responses via a `requestToken` ref (same pattern as `customerSlice.searchToken`). Reach for it for customers (used in `SaleFormSheet`) and any future large-entity picker. Don't migrate small static-list dropdowns — `Dropdown` is fine there.

38. **`app_options` is global config + seeds the default LBP currency** — `app_options` is a single app-wide key/value table (no `tenant_id`), managed by the SaaS owner from SuperAdmin's **Options** tab (full CRUD, service-role writes) and read-only in SubsTrack (`options` module + `optionSlice`, fetched at app bootstrap **and** re-primed in `primePostAuth`, **not** reset on `logout`; RLS = `anon` + `authenticated` `SELECT`, since some flags gate pre-auth UI). The `LiraRate` row holds the default USD→LBP rate. Other seeded flags: `AllowPlanUpgrade` (swaps the upgrade button for a WhatsApp "contact to upgrade" deep-link to `SupportWhatsAppNumber`), `AllowSelfServiceSignup` (hides the login "Create organization" button **and** is enforced in the `create-tenant` edge function). Read flags via the typed hooks in `useOptionSlice.ts` (`useCanUpgradePlan` / `useSelfServiceSignupEnabled` / `useSupportWhatsAppNumber`), never by poking `items` directly. On tenant creation BOTH paths — SuperAdmin `TenantService.createTenant` and the public `create-tenant` edge function — auto-seed an `LBP` currency (`decimals 0`, symbol `ل.ل`) whose `rate_per_usd` is copied from `LiraRate` (falling back to `DEFAULT_LIRA_RATE = 89000` when missing/invalid, so a bad option never blocks signup). The seed is a one-time starting value, not a live link — the tenant edits its own LBP rate afterward. Option keys are immutable after creation; reference them via `OPTION_KEYS`.

39. **Keyboard avoidance uses `react-native-keyboard-controller` — never RN's built-in `KeyboardAvoidingView`** — `app.json` has `edgeToEdgeEnabled: true` (Expo SDK 54 default). In edge-to-edge mode the Android window no longer resizes when the keyboard opens, so RN's `KeyboardAvoidingView` (`behavior="height"`) has nothing to shrink and the lower fields of a long form stay trapped under the keyboard (the bug shows up on real devices / release APKs, not always in dev). The fix is the Expo-recommended `react-native-keyboard-controller`: a single `<KeyboardProvider>` wraps the app at [app/_layout.tsx](../SubsTrack/app/_layout.tsx) (inside `GestureHandlerRootView`). Two layout shapes, two tools:
    - **Plain full-scroll screens** — `LoginScreen` (and any non-sheet form screen) — use `<KeyboardAwareScrollView … bottomOffset={24}>` (drop-in for the old `KeyboardAvoidingView` + `ScrollView` pair). It auto-scrolls the focused `TextInput` above the keyboard and adds bottom inset so the submit button is always reachable. **Note:** form *sheets* are no longer here — since the Gorhom migration (gotcha #45) every `*FormSheet` uses `FormSheet` (a `BottomSheetScrollView` + `BottomSheetTextInput` via `useSheetTextInput`), and Gorhom owns their keyboard avoidance (`keyboardBehavior="interactive"`), so they don't touch `KeyboardAwareScrollView` at all.
    - **Sticky-footer layouts** — the two signup screens (inner `ScrollView` + a sibling footer button-bar) — use the library's drop-in `<KeyboardAvoidingView behavior="padding">`. `KeyboardAwareScrollView` is wrong here: it would detach the sibling footer. (The bottom-sheet pickers no longer pass a `wrap` — Gorhom handles their keyboard now.)
    - Works inside RN `<Modal presentationStyle="pageSheet">` out of the box (keyboard-controller ≥ 1.13 added Android Modal support; iOS always worked) — no nested provider needed. It's a native module: `react-native-reanimated` is the peer dep (already installed), no app.json config plugin is required (autolinked), but adding it means a **dev/EAS rebuild** (not hot-reloadable, not Expo Go — see "Running the Apps").  NativeWind `className` still works on these components via the `jsxImportSource: 'nativewind'` transform.
    - **iOS caveat (verify-on-device):** `KeyboardAwareScrollView` inside a `.pageSheet` UIKit sheet has a documented flicker history ([issue #726](https://github.com/kirillzyusko/react-native-keyboard-controller/issues/726)) and all the form sheets use `<Modal presentationStyle="pageSheet">`. Android (the primary target) is unaffected. If caret-scroll flicker shows up on iOS, the fallback is to use this library's `<KeyboardAvoidingView behavior="padding">` (or `mode="insets"`) for the pageSheet forms instead — smoke-test before shipping iOS.

40. **Edge-function errors must be parsed, not passed straight to `handleError`** — `supabase.functions.invoke` collapses ANY non-2xx response into a generic `FunctionsHttpError` whose `.message` is the useless `"Edge Function returned a non-2xx status code"`. The function's real message lives in the JSON body on `error.context.response` (a `Response`). Repos that invoke edge functions (`UserRepository.create`/`delete`/`updatePassword`) call **`await this.handleFunctionsError(error)`** ([BaseRepository.ts](../SubsTrack/src/core/utils/BaseRepository.ts)) instead of `handleError` — it reads the body via `readFunctionsErrorBody` ([functionsError.ts](../SubsTrack/src/core/utils/functionsError.ts)) and surfaces the server's message (e.g. `"Forbidden: admins can only change passwords of staff users"`), falling back to the generic handling when there's no body. `SignupRepository` uses the same `readFunctionsErrorBody` helper directly (it also needs the `code` field). Any new edge-function call site must follow this pattern, or users see the meaningless "non-2xx" text.

41. **A customer's plans live in `customer_plans` (service lines), not `customers.plan_id`** — `customers.plan_id` was removed. A `CustomerPlan` row = one plan a customer is subscribed to, with its own `start_date` / `cancelled_at`; `plan_id` may be NULL (custom/occasional line). **Plans are managed inline in the customer form** (`CustomerFormSheet` → "Plans" section, create AND edit) — add / change / remove rows there, NOT from the month-grid panel (its line selector is view-only). On save the form creates/updates the customer then calls the `customerPlans` slice's single action `syncLines(customerId, lines, removedIds, tenantId)` ([customerPlanSlice.ts](../SubsTrack/src/state/slices/customer-plans/customerPlanSlice.ts)), which deletes removed lines then creates/updates the rest and calls `get().customers.fetchCustomer(customerId)` so the customer object (single source of truth for its lines) and the grids rebuilt from it refresh. **Remove** = `CustomerPlanService.deleteLine` → hard-delete a line with no payments, else soft-cancel (`active = false`) so payment history is never lost (rule #7). The form keeps **≥1 row** (a plan-less row records custom amounts), so every customer has ≥1 line. Lists/details load lines via `.select('*, customer_plans(*, plans(*))')` → `customer.customerPlans`. `payments.customer_plan_id` is the structural link (which line a payment settles); `payments.plan_id` stays as the price/plan **snapshot** (gotcha #2). Branch is inherited from the customer (no `branch_id` on `customer_plans`; RLS + `BRANCH_SCOPES.customer_plans = inherited`).

42. **A sale's collector cash is `amount_paid`, not `total_amount`** — sales revenue reports sum `total_amount` (what was sold), but the cash a collector physically holds from a sale is `amount_paid` (what was collected; a partial sale leaves the rest as a debt). The **Collector Wallet** therefore reads `amount_paid` for sales (like payments/debt_payments), never `total_amount`. Using `total_amount` would overstate a collector's cash by the unpaid portion. (`WalletService.collectItems` → `saleService.getUnremittedForWallet`.)

43. **Re-paying a voided month must reset `remitted_at`/`remitted_by`** — payments upsert on `(customer_plan_id, billing_month)`, so re-recording a voided month **reuses the same row**. If that row was previously handed over (remitted), the new cash would wrongly look already-remitted. Both write paths null the remittance on re-pay: the web `PaymentRepository.create`/`createMany` upsert object and the offline `buildRow` set `remitted_at: null, remitted_by: null` (and the offline `ON CONFLICT DO UPDATE` copies them via `excluded.*`). This is the reason the Collector Wallet uses **columns on the row** instead of a separate settle/link table — a link keyed by the reused payment id would go stale on re-pay; a column resets cleanly. `custom_debts` has **no** remittance columns (a custom debt isn't collected cash). Editing a payment's `amount_paid` does **not** touch `remitted_at`, so editing an already-remitted payment changes the historical handover figure but not the current wallet (which only counts unremitted rows).

44. **Back closes an open sheet / dialog (Android hardware-back + browser Back on web)** — Native and web use different machinery:
    - **Native Android hardware-back:** **Gorhom does NOT handle this** — v5 contains no `BackHandler` anywhere (not in `BottomSheetModal`, not in `BottomSheetModalProvider`), and its sheets aren't RN `Modal`s, so nothing routes back through `onRequestClose` either. Assuming otherwise was a real bug: Back popped the Expo Router route while the sheet stayed on screen. Fix: `useAndroidBackDismiss(active, onDismiss)` ([useAndroidBackDismiss.ts](../SubsTrack/src/shared/hooks/useAndroidBackDismiss.ts)), called by `AppBottomSheet` for **every** variant (a popup must swallow Back too, or Back navigates out from under it). It needs no shared stack: RN fires `hardwareBackPress` listeners **newest-first**, so a stacked sheet — or a selection bar activated inside one (`useSelectionBackHandler`) — is dismissed before whatever sits below it. Centered dialogs (`ConfirmDialog`, `UpgradePromptModal`) are plain RN `Modal`s and do route hardware-back through `onRequestClose`.
    - **Web browser-Back:** RN-Web ignores browser history, so Back would pop the Expo Router *route* while the sheet stays open. Fix: `useWebBackDismiss(active, onDismiss)` ([useWebBackDismiss.ts](../SubsTrack/src/shared/hooks/useWebBackDismiss.ts)) — web-only (no-op on native). **Scope — every open surface:** `AppBottomSheet` registers for **both** variants, and the centered dialogs (`ConfirmDialog`, `UpgradePromptModal`) call it directly — a dialog **must** trap Back too, else Back would close the sheet *underneath* it and leave the dialog floating. `ConfirmDialog` guards `loading` so Back can't dismiss mid-confirm. (The `auto` popups — pickers + `ActionMenu` — were once excluded to cut history churn; that left Back falling through to the router whenever a popup was the top surface, changing the screen and taking the popup with it. The per-modal sentinel + per-tick reconcile is what makes their churn safe.)
    - **The sentinel must carry the router's `history.state`** — `pushSentinel` does `pushState({ ...window.history.state, __modal: true }, "")`, **not** `pushState({ __modal: true })`. Expo Router keeps its history-entry `id` in `window.history.state` and locates itself with it (`createMemoryHistory.index` returns **0** when the id is missing). With an id-less sentinel as the current entry, any navigation-state change reaches Expo Router's `history.replace()`, which mints a **new** id, can't find it in its `items` array, and therefore **resets that array to a single entry** — the router's whole back-history is gone. The next Back then resolved to the wrong record and the router did a `resetRoot` on top of our dismiss: **the sheet closed AND the screen navigated**. Copying the current state keeps the sentinel invisible to the router.
    - **How the hook works:** it keeps a shared LIFO stack of open modals and maintains **one throwaway `history` "sentinel" entry per open modal** (`sentinelCount` tracks `dismissStack.length`). A user Back pops the topmost sentinel (URL/route unchanged), fires `popstate`, and we dismiss the **topmost** modal; because history holds as many sentinels as open modals, the next Back already has its own sentinel — nothing is re-armed in the handler. Closing any other way (Cancel/Save/unmount) drops a sentinel via our own `history.back()` (ignored via a `selfPops` counter). **Why one sentinel PER modal (not a single re-armed one):** with a single sentinel, each Back consumed it and a fresh one had to be `pushState`d from inside the popstate handler; a **second Back pressed faster than that async re-arm round-trip** navigated against a history with no sentinel left and fell straight through to the route — closing the tab or jumping pages. Keeping the sentinel count equal to the modal count means every Back, however fast, always has a sentinel to consume. **Why still reconcile once per tick (not push/pop eagerly):** a modal handoff — one modal closing while another opens/closes in the **same tick** (menu → delete-confirm; confirm → close-parent-sheet) — would otherwise fire an async `history.back()` that overlapped a sibling's `pushState`/`back()`; the browser then popped one step too many and **exited the route**. Coalescing the stack ⇄ history diff into one reconcile per tick (via `queueMicrotask`) means such a handoff nets to "same depth" and touches history not at all, so `back()` and `pushState` never interleave.

45. **Every sheet is a Gorhom bottom sheet; confirmations stay centered** — The whole app's sheet system is `@gorhom/bottom-sheet` (v5), built on **one core**, `AppBottomSheet` ([AppBottomSheet.tsx](../SubsTrack/src/shared/components/AppBottomSheet.tsx)): it wraps a Gorhom `BottomSheetModal` (rendered through the `BottomSheetModalProvider` at [app/_layout.tsx](../SubsTrack/app/_layout.tsx)) and **bridges the app's declarative `visible`/`onDismiss` to Gorhom's imperative `present()`/`dismiss()`**. The bridge tracks Gorhom's **real** open/closed state via `onChange` (`openRef`) and only presents when closed / dismisses when open (see the present/dismiss gotcha under `BottomSheetScaffold` below). The dismissal handler checks `visible` to distinguish a user close (drag / backdrop / hardware-back — caller still has `visible=true`, so we propagate `onDismiss`) from a programmatic one (caller already set `visible=false`, we called `dismiss()` — swallow it), so `onDismiss` fires exactly once and never re-enters. Gorhom gives drag-down-to-close and backdrop-tap-to-close (`BottomSheetBackdrop` `pressBehavior="close"`) out of the box; Back is wired by the app (#44). There is **no** hand-rolled Reanimated sheet, no `animationType`/web instant-close hack, and no `wrap` prop anymore — Gorhom owns keyboard handling (`keyboardBehavior="interactive"` + `android_keyboardInputMode="adjustPan"`). **`android_keyboardInputMode` must NOT be `adjustResize`:** that value tells Gorhom "the Android window resizes itself when the keyboard opens, stay out of it" — and Gorhom then literally sets `keyboardHeightWithinContainer = 0` and returns. Untrue here: `app.json` has `edgeToEdgeEnabled: true` (gotcha #39), so the window never shrinks. The sheet kept its full 92% height, its bottom sat under the keyboard, and **the last fields of a long form could not be scrolled to**. `adjustPan` (Gorhom's default) lets its own `interactive` handling shrink the content box to the space above the keyboard. **No native rebuild was needed:** Gorhom rides on `react-native-reanimated` + `react-native-gesture-handler` (both already native-built) and ships no native module of its own. Two variants, two public wrappers:
    - **`BottomSheetScaffold`** (`variant="auto"`, content-height via `enableDynamicSizing`, capped by `maxDynamicContentSize`) — every transient tap-outside popup: `Dropdown`/`DropdownModal`, `DatePickerInput`, `CurrencyInput`, `AsyncEntityPicker`, `ActionMenu`. **Present/dismiss lifecycle gotcha:** these popups are **always mounted** and toggle `visible`, so they get `visible=false` passes *before* first open, and after every user-gesture close they get a `visible=true → onDismiss → visible=false` sequence. Calling Gorhom's `present()`/`dismiss()` **out of sync with the sheet's real state wedges it** — the next call silently no-ops (no animation, no `onChange`). This caused two bugs in turn: first **every** picker/menu/dropdown failed to open at all (a `visible=false` pass called `dismiss()` on a never-presented modal); then, after a naive first-present-only guard, they opened **exactly once** and never again (the redundant `dismiss()` that follows a gesture close wedged them). Fix: `AppBottomSheet` tracks Gorhom's actual index via `onChange` in an `openRef` and gates **both** calls on it — `present()` only when `!openRef`, `dismiss()` only when `openRef` — making the bridge idempotent against every redundant `visible` pass. Any new always-mounted sheet inherits this for free (it lives in the shared core). **Long-list gotcha:** a long/paginated list should own the sheet height — pass **`scrollable`** to `BottomSheetScaffold` (only `AsyncEntityPicker` does — it paginates) → `AppBottomSheet` uses a FIXED snap (`70%` of the frame) with a `flex:1` body so the list fills the sheet. Give that list `flex:1`, not `maxHeight`. Short lists (`Dropdown`, `CurrencyInput`) and fixed-height content (`DatePickerInput`'s columns) keep dynamic sizing with a `maxHeight` cap — a 2-item list then hugs its content instead of ballooning to 70%. **A dynamically-sized body must use PLAIN RN scrollables — see #47.**
    - **`FormSheet`** ([FormSheet.tsx](../SubsTrack/src/shared/components/FormSheet.tsx), `variant="full"` = a `~92%` snap point) — every form/detail sheet: it owns the shared chrome (Gorhom drag handle + a header of *title + one dismiss action* + a `BottomSheetScrollView` body inside `ResponsiveContainer`). Used by Customer / Sale / Payment / Bulk-payment / User / Plan / Product / Currency / Custom-debt / Debt-payment forms, the Payment/Sale detail sheets, and the Developer import sheet. **Replaced the old `SheetModal`, which was deleted.** A trailing `UpgradePromptModal` sits as a sibling next to `FormSheet` in a Fragment (it's a centered RN `Modal`, renders above the sheet).
    - Sheets with a **non-standard body** build on `AppBottomSheet variant="full"` **directly** (not `FormSheet`): `DebtHistorySheet` (a `BottomSheetSectionList`), and `DebtorDetailSheet` + `WalletsScreen`'s collector sheet (custom header + `BottomSheetScrollView`).

Gorhom's *content* pan gesture is the one thing that can stop a sheet body from scrolling, and it does so two ways: it swallows the vertical drag of any non-Gorhom list (this is why the payments-history sheet's plain `SectionList` was frozen), and it hard-**locks** even Gorhom's own scrollables — `useScrollable` reports `SCROLLABLE_STATUS.LOCKED` unless the sheet is *exactly* at its extended position, and a locked scrollable is snapped back to its offset on every scroll event. Disabling it makes the body a normal scroll surface: **any** list works, plain or Gorhom. The sheet is still dragged down by its **handle**, and closes via backdrop tap, Back (#44) and its own Cancel/Close action — only "drag the sheet down from anywhere in its body" is given up, which a 92%-tall page-like sheet does not need. The small content-hugging `auto` popups (`Dropdown`, `ActionMenu`, `DatePickerInput`, `CurrencyInput`) turn it off **too** — they had to, because their lists became plain RN `FlatList`s (#47) and a plain scrollable cannot scroll under the content pan. Taps on the header's Cancel / Close / Confirm buttons still work (a pan only activates on movement). Applied to `FormSheet` (so every form sheet gets it), `DropdownModal`, `CurrencyInput`, `DatePickerInput`, `AsyncEntityPicker`, and the four sheets that build on `AppBottomSheet` directly (`PaymentsHistorySheet`, `DebtHistorySheet`, `DebtorDetailSheet`, the Wallets collector sheet). **Never wrap a list in it** — that is content panning again with the same freeze, and worse: the HANDLE source deliberately ignores the scroll offset (only `GESTURE_SOURCE.CONTENT` reads `scrollableContentOffsetY` and yields the gesture back to the list), so the sheet would drag away from under a half-scrolled list. A body with **no** scrollable is the one safe exception — `ActionMenu` wraps its ENTIRE menu (title + the plain column of rows) so the popup drags from anywhere, with `activationDistance={12}` (→ `activeOffsetY`) so the pan only takes over after 12pt of vertical travel and a slightly sloppy tap still presses the row.

Nested sheets (a form opening a picker, or `SaleFormSheet`/debt forms opening `CustomerFormSheet`) rely on Gorhom `BottomSheetModal` stacking — supported.
    - **Width cap on web needs `width` + AUTO side margins on the hosting container** — on a wide browser window a sheet would stretch edge-to-edge and no longer line up with the page column (`ResponsiveContainer`, `max-w-3xl` = 768px). `AppBottomSheet` passes `containerStyle={{ width: 768, marginHorizontal: "auto" }}` (web only, and only when the window is wider than that). Nothing else works: the sheet body is `position:absolute` and Gorhom re-applies `left:0/right:0` **after** our style, so `left` is overridden, `paddingHorizontal` on the parent never insets an absolutely-positioned child on web, and `width` alone leaves the box over-constrained — the browser then drops `right` in LTR (pinned left) and `left` in RTL (pinned right). Auto margins are the one CSS rule that still centers an over-constrained absolute box, and it is direction-agnostic, so LTR and Arabic RTL both center. The cap goes on the **hosting container**, not on Gorhom's `style`/`snapPoints`: the backdrop is the container's sibling, so it keeps covering the whole window, and height measurement is untouched. Native stays edge-to-edge (the platform convention) — the Yoga/CSS absolute-layout rules above are not identical, so the style is web-gated rather than shared.
    - **Confirmation / message dialogs (`ConfirmDialog`, `UpgradePromptModal`) intentionally stay CENTERED** RN `Modal`s (`animationType="fade"` + `justify-center`) — they are decisions/notices, not sheets, and can stack on top of a form sheet. Build any new picker/menu on `BottomSheetScaffold`, any new form on `FormSheet`; keep confirmations centered.

46. **Tappables use gesture-handler's `Pressable`, NOT react-native's touchables** — the shared `PressableOpacity` ([PressableOpacity.tsx](../SubsTrack/src/shared/components/PressableOpacity.tsx)) — the base for virtually every button/row/menu-item in the app (`Button`, `FAB`, `EntityCard`, `PageHeader`, `Dropdown`, `ActionMenu`, `SegmentedTabs`, `ConfirmDialog` actions, …) — wraps `Pressable` from **`react-native-gesture-handler`**, not any touchable from `react-native`. **The bug it fixes:** RN's `Touchable*`/`Pressable` use the JS **responder** system, a separate world from `react-native-gesture-handler` (what Gorhom's sheets pan with, #45). When a sheet is closed **by dragging it down**, the native gesture system stays "hot" for one more touch to settle the just-finished pan; that first tap on an RN touchable gets **granted then terminated** — `onPressIn` fires (you see the opacity/press effect) but `onPress` never does, so the tap is silently eaten and the user must tap twice. Closing the sheet by **tapping the backdrop** never activates a pan, so it never showed the bug — the asymmetry that fingerprints this cause (NOT an overlay: the press effect proves the touch reaches the button). gesture-handler's `Pressable` lives in the same gesture system, so it isn't terminated and the first tap works. **Why `Pressable` and not gesture-handler's `TouchableOpacity`:** RNGH's `TouchableOpacity` renders **two nodes** (an outer `containerStyle` view + an inner `style` view), so a single `className` reaches only one — layout classes like `flex-1` / absolute positioning land on the wrong node and silently break (e.g. `SegmentedTabs`, dialog button rows collapsed). RNGH's `Pressable` is a **single styled view** (like RN's old touchable), so `className` behaves identically everywhere with **no per-component special-casing** — the root fix, not a patch. **Two things make it work:** (1) `PressableOpacity` calls `cssInterop(Pressable, { className: "style" })` at module load — NativeWind auto-maps `className`→`style` for RN's *core* components but NOT gesture-handler's, and without it the classes **silently drop at runtime** (tsc still passes — NativeWind augments the *type* globally) so cards/buttons lose their chrome while inner `View`s stay styled. (2) Press feedback is a baked-in **`active:opacity-60`** class (not `TouchableOpacity`'s animated fade — it's an instant toggle); NativeWind injects the press handlers that drive the `active:` state onto any `cssInterop`'d component. Any new tappable should go through `PressableOpacity`; never reach for RN's `Touchable*`/`Pressable` for an interactive control that can sit under or near a sheet.

47. **A content-sized (`auto`) sheet must contain PLAIN RN scrollables, never Gorhom's** — Gorhom's dynamic sizing keeps **one** number, `animatedLayoutState.contentHeight`, and the sheet's height is exactly `contentHeight + handleHeight` (capped by `maxDynamicContentSize`). **Two different components write that same number:** `BottomSheetView` writes its measured layout height (`onLayout`), and EVERY Gorhom scrollable (`BottomSheetFlatList`/`ScrollView`/`SectionList`, via `useBottomSheetContentSizeSetter` on `onContentSizeChange`) writes **its own scroll-content height** — which knows nothing about the sibling header, the search box, or the safe-area padding, and ignores the list's own `maxHeight`. Last writer wins, so the sheet height was a race. **The bug (Android):** in the currency picker and the product dropdown the `BottomSheetFlatList` reported just the rows (e.g. 4 rows ≈ 210px) and overwrote the `BottomSheetView`'s correct total (header 45 + list + bottom inset ≈ 280px) → the sheet opened ~70px too short and, because `BottomSheetView` is `position:absolute` (it lays out from the top, unclipped by the sheet), the **last rows were cut off below the sheet's bottom edge** with nothing to scroll. The same race produces the opposite symptom with a long list (list reports 1200px → clamped to 90% of the frame → a tall sheet with a big empty gap), and `DatePickerInput`'s 3–5 side-by-side columns each reported their own 1364px content and blew the sheet up to full height. **Fix:** the `auto` bodies use plain RN `FlatList` (`Dropdown`, `CurrencyInput`, `DatePickerInput`), so `BottomSheetView` is the **single** writer of `contentHeight` and the sheet always matches its body; a plain list only scrolls once the content pan is off, so `AppBottomSheet` now disables `enableContentPanningGesture` for **every** variant (#45). Cap such a list with `maxHeight`, never `flex:1` (a `flex:1` child of an auto-height parent collapses). **Gorhom scrollables stay correct in FIXED-snap sheets** (`FormSheet` / `variant="full"` / `auto scrollable`) — `enableDynamicSizing` is off there, so `setContentSize` no-ops. Also: the fixed-snap `auto` body now gets `paddingBottom: insets.bottom` in `AppBottomSheet` (a `full` body pads its own scroll area in `FormSheet`), without which `AsyncEntityPicker`'s last row sat under the Android nav bar.

48. **Product stock is a ledger sum, and four things about it are easy to get wrong** — stock on hand is `SUM(stock_movements.quantity_delta)` over non-voided rows, never a column (a counter would be clobbered by the whole-row, latest-`updated_at`-wins push in `sync.ts`). Four traps:
    - **The RLS policy must mirror `products_select`, NOT `sale_items_all`.** Both are child tables that inherit a parent's branch, so copying the nearer neighbour is the obvious move — and it's wrong. `sale_items_all` inherits `sales`, which is **owned** (`s.branch_id = current_branch_id()`, no NULL branch). `stock_movements_all` inherits **`products`**, which is **shared** (`OR p.branch_id IS NULL`). Without that `IS NULL` clause a branch-scoped user sees zero movements for every SHARED product → each reads as out of stock → **unsellable for them, with no error to explain it**. The `WITH CHECK` needs the same allowance (and so deliberately diverges from `products_modify`, which *does* stop branch users creating shared products): a branch user who can sell a shared product must be able to insert its movement, or every such sale poisons the push batch (below).
    - **Voiding a sale soft-voids its movements; it does NOT insert opposite ones.** `UPDATE stock_movements SET voided_at = … WHERE sale_id = ? AND voided_at IS NULL` is one statement regardless of line count, and re-running it is a no-op. Compensating rows would be neither: `OfflineSaleRepository.voidSale`'s `UPDATE … WHERE voided_at IS NULL` ignores its result and still returns the row, so an already-voided sale (e.g. voided on another device and pulled down) "succeeds" locally and would credit the stock a second time. Note this diverges from the web path, which throws (`.is('voided_at', null)` + `.single()` → 0 rows).
    - **Never add a `stock >= 0` constraint or trigger.** Two devices offline can each legitimately sell the last unit. A DB-level check would make a legitimately-recorded sale permanently un-pushable — and because `pushDirty` upserts a table's dirty rows as **one batch**, that single bad row would freeze *every* stock movement from that device forever. Blocking lives in `SaleService.assertStockAvailable` and is **advisory**; negative on-hand must stay representable and is rendered as "Short by N".
    - **A local product hard-delete must cascade to the mirror's movements by hand.** The server FK cascades, but the SQLite mirror declares no FKs (rows arrive out of order during pull), so `OfflineProductRepository.delete`/`deleteMany` delete the `stock_movements` rows in the same `write()`. Skipping this leaves a dirty movement pointing at a product the server never saw → FK error → the poisoned batch above. No `markDeleted` for the children; the server-side cascade covers them.

    Two more, less dangerous: `quantity_delta` must stay `'int'` in `db/tables.ts` (`'num'` maps to TEXT, and `SUM()` over TEXT compares by storage class), and the `product_stock` view **must** carry `WITH (security_invoker = true)` (PG 15+) — without it the view runs as its owner and leaks every tenant's stock.

49. **A single-target SQLite UPSERT can't guard a table with TWO unique constraints** — the mirror's `payments` has both `id` (primary key) and `UNIQUE (customer_plan_id, billing_month)`, and the id is *derived* from that key (`deterministicId`). The old write was one `INSERT … ON CONFLICT (customer_plan_id, billing_month) DO UPDATE`, and SQLite applies an upsert to the **named target only**: the moment a mirror row's id and key drift apart (an id-carrying row pulled back under a different key, a mirror row left with a NULL `customer_plan_id` — NULLs are distinct in a UNIQUE index, so the key target silently never matches while every such row hashes to the SAME id), the insert stops being healed and fails hard with `UNIQUE constraint failed: payments.id`. The user then can **never** record that month on that device again — recording a second plan's month after the first was paid was the reported symptom. `upsertNaturalKeyDirty` therefore resolves the target row with a `SELECT` (by natural key, then by id) and returns **the id it actually stored**; the pull applies `clearNaturalKeyDuplicate` for the mirror-image case (a server row whose key is held locally under another id, which used to abort the payments pull every cycle). It is generic over `NATURAL_KEYS`, which now also holds **`skipped_months`** (same `(customer_plan_id, billing_month)` key) — anything else keyed this way must go through it too — and note the corollary: a create that upserts must never return its *intended* id, only the stored one, or the caller holds a Payment whose row doesn't exist and its next void/edit quietly misses.

50. **Dashboard revenue is CASH COLLECTED, never billed value** — all three streams sum only money received: `payments.amount_paid` + `sales.amount_paid` + `debt_payments.amount`, each scoped by when the money arrived (`paid_at` / `sold_at`, never `billing_month`). It is tempting to reach for `sales.total_amount` (it looks like "the sale"), but that counts money nobody has handed over: the unpaid part of a partial sale is a **debt**, and it enters revenue only when collected, in the debt payment's month. Get one stream wrong and the total is neither cash nor billed — the original bug was sales counting `total_amount` (overstating) while collected debts counted **nowhere at all** (money vanishing from revenue forever). The invariant to preserve: every collected amount appears in exactly one month's revenue, exactly once. Note the asymmetry this creates on purpose — `salesCount` counts every sale row paid or not, and the Debts categories still read `total_amount - amount_paid`; only the *money* is cash-based. `sale.monthlyTotals` (the Sales-tab month headers) follows the same rule, matching `payment.monthlyTotals`.

51. **A bottom sheet can't start animating until JS stops rendering — so a form's body is deferred one frame** — Gorhom only calls `snapToIndex` once the sheet container has been laid out by native (`BottomSheet.tsx`: `handleSnapToIndex` early-returns while `isLayoutCalculated` is false), and that layout event cannot be dispatched while the JS thread is busy. Opening a form used to run **three sequential commits** before anything moved: (1) the parent screen re-renders and mounts the form — `BottomSheetModal` returns `null` until presented, so the body renders nowhere yet; (2) `present()` defers its own work by a `requestAnimationFrame`, then flips `mount: true`, rendering a `<Portal>` that is also `null`; (3) the portal registers its children in a `useEffect`, so the **entire form body finally renders inside the root portal host** — and only after that native layout, and the slide, could begin. The visible symptom is a dead gap after the tap, scaling with form size, not a slow animation. **Fix:** `FormSheet` renders its body one frame late via `useAfterFirstFrame` ([useAfterFirstFrame.ts](../SubsTrack/src/shared/hooks/useAfterFirstFrame.ts)); the header shows immediately and the fields land while the sheet is already moving on the UI thread. This is only safe because a `full` sheet has a **fixed** snap point — never do it for a content-sized `auto` sheet, whose height is measured *from* its body (#47). Always-mounted sheets must pass their visibility (`useAfterFirstFrame(visible)`), or the frame is spent at screen mount and the deferral does nothing on the real open. Also fixed alongside: Gorhom's default open animation is platform-split (`constants.ts`) — a stiff spring on iOS but a 250ms `Easing.out(Easing.exp)` curve on **Android**, so `AppBottomSheet` passes a shorter Android-only `animationConfigs`.

52. **`// eslint-disable … react-hooks/*` silently switches React Compiler OFF for the whole file** — `app.json` has `experiments.reactCompiler: true`, so `babel-preset-expo` runs `babel-plugin-react-compiler` and auto-memoizes every component and hook. But the compiler **refuses to optimize any file containing a React-ESLint disable comment** ("React Compiler has skipped optimizing this component because one or more React ESLint rules were disabled") — it assumes the suppressed rule means its analysis can't be trusted. 31 files (every screen and every form sheet) carried a `react-hooks/exhaustive-deps` disable for the usual "run on mount only" effect, so the app was paying for the compiler and getting nothing back on exactly the components that needed it. **The disable is almost never necessary here: Zustand slice actions are created once in the slice creator and never reassigned** (immer's `set` copies function properties by reference; `reset()` only touches data fields), so listing them in the dep array is free — the effect still runs once. Same for `useSelection().clear` and any `useCallback([])`. Two things that DO need care: depend on `selection.clear`, never on the `selection` object (the hook returns a fresh object each render → infinite loop), and a plain `async function` used by an effect must become a `useCallback` first (note it is then no longer hoisted, so declare it above the effect). Two other compiler bail-outs worth knowing: **reading a ref during render** (`key: \`row-${rowKey.current++}\`` inside a `useState` initializer — hence `makeRow(suffix)` in `CustomerPlansEditor` / `SaleItemsEditor`), and **`try` with a `finally`**, which this compiler version rejects outright (both `try/finally` and `try/catch/finally`). The `finally` blocks that reset a busy flag are correctness-critical, so they stay — the ~13 list screens holding one are simply not auto-memoized, and anything expensive in them needs a hand-written `useMemo` (see the memoized list element in `CustomerListScreen`). Verify with `babel-plugin-react-compiler`'s `logger.logEvent` before assuming a component is optimized.

53. **OTA updates are gated by a fingerprint you never type** — `app.json` sets `runtimeVersion: { policy: "fingerprint" }`, so `@expo/fingerprint` hashes the native inputs (autolinked native deps, `plugins`, native `app.json` fields, `patches/`, and **`package.json` → `scripts`**) and `eas update` only reaches phones whose baked-in label matches exactly. Editing `src/`/`app/` never changes the hash; adding an npm script or a native dependency does — and then updates **silently stop arriving**: no error, no crash, just "no update found" until you ship a new build. `eas update` prints the fingerprint it published for; `npm run ota-fingerprint` prints the local one — compare them first whenever an update doesn't land. Add a `.fingerprintignore` only if it starts churning for non-native reasons. Two related notes: `expo-updates` was in `package.json` long before OTA existed, purely for `reloadAsync()` on the RTL language switch (#5), which now also applies a pending update; and the APK a user already has can only receive OTA if it was built **after** `updates.url` + `channel` existed — pre-OTA builds are permanently cut off.

53b. **…and on Windows, CRLF line endings alone break it** — the fingerprint hashes two tracked text files **byte-for-byte**: `eas.json` (`reasons: ["easBuild"]`) and `.gitignore` (`["bareGitIgnore"]`). EAS Build runs on **Linux** (LF), but a Windows checkout with `core.autocrlf=true` writes **CRLF**, so the very same commit fingerprints differently on each side. Real symptom: a `preview` build reported runtime `a01ebec…`, every `eas update` from Windows published under `1d23cca…`, and the app just never saw an update — `eas update` says "success", the phone says nothing. The repo-root **`.gitattributes` (`* text=auto eol=lf`) is what keeps the two in sync** — do not delete it, and after adding it the *existing* working tree still holds CRLF until the files are re-checked-out (`git add --renormalize .`, or delete + `git checkout -- .`). Note `git status` can flag a freshly converted file as modified purely on the cached size while `git diff` is empty — `git add` it to refresh the stat. Everything else in the hash is immune: `node_modules/**` comes from npm tarballs (LF on both), the icon is binary, and `package.json` / `app.json` are hashed as *parsed* JSON. Diagnose with `node node_modules/expo-updates/bin/cli.js fingerprint:generate --platform android`, which prints every source and its hash (`npm run ota-fingerprint` prints only the final hash), or `eas fingerprint:compare --build-id <id>`.

54. **The unsaved-changes prompt lives in ONE place, and a competing back handler is what breaks it** — `AppBottomSheet` takes a `dirty` prop and routes **every** close path through `useUnsavedChangesGuard` ([useUnsavedChangesGuard.ts](../SubsTrack/src/shared/hooks/useUnsavedChangesGuard.ts)), so no form wires the dialog itself: the header button reads the guarded dismiss from `SheetDismissContext` (`FormSheet` splits its body into an inner component just to consume it), Back comes through the two back hooks, the drag is caught in Gorhom's `onAnimate` when `toIndex === -1`, and the backdrop through its `onPress`. Four traps, all found the hard way: (a) **`pressBehavior="none"` makes the backdrop inert** — Gorhom drops the whole tap `GestureDetector` for `"none"`, so `onPress` never fires; use a numeric `pressBehavior={0}` (a no-op snap on a single-snap sheet) to keep the detector mounted. (b) **The prompt must own Back while open — and the two platforms need OPPOSITE wiring to get there.** The dialog is an RN `Modal` taking Back via `onRequestClose`, so on **Android** the sheet's own `hardwareBackPress` listener must be *gone* while the prompt is up (`BackHandler` fires newest-first, so otherwise one press answered the dialog *and* re-closed the sheet, which re-asked and eventually let a press reach the router). Hence the guard returns `[guardedDismiss, asking]` and `useAndroidBackDismiss` gets `visible && !asking`, with `asking` cleared *after* the dismiss/reopen callback. On **web the same deregistration is a bug**: `useWebBackDismiss` mirrors its stack depth in real history, one sentinel per entry, so dropping the entry mid-ask abandoned a sentinel — the browser had already eaten the sheet's on the Back press, the dialog pushed a *replacement* rather than a second one, and the dialog's own close then ran `history.back()` straight past it into the route ("discard takes me to the previous page", with no second popup). The sheet therefore stays registered on web and passes a **`defersClose`** predicate (`() => dirty`) instead; `handlePopState` peeks at the top entry, and when it defers it keeps the entry, re-pushes the consumed sentinel via `scheduleReconcile()`, and fires the dismiss. Do not "simplify" either side to match the other. (c) **A drag is intercepted, not undone** — `onAnimate` is a JS-thread callback (`runOnJS`) fired *before* the animation starts, so `expand()` snaps the sheet back and the dialog appears over a sheet still on screen; it's best-effort (a JS stall can let the close finish, and `onDismiss` is the net that re-presents it). (d) **Dialog lifecycle** — `confirmSlice.show` now settles any outstanding prompt with `false` before installing a new resolver, and the guard settles on unmount; without either, a competing `confirm()` caller or a sheet torn down mid-prompt left an `await` that never resumed and a dialog floating over an empty screen.

55. **A "dirty form" check is a BASELINE diff, and the usual false positive comes from a child seeding a field after mount** — `useDirtyForm` ([useDirtyForm.ts](../SubsTrack/src/shared/hooks/useDirtyForm.ts)) captures the first render's values in a lazy `useState` initializer (never a ref assigned during render — #52) and shallow-compares. That makes "changed it back to the original" correctly clean, but it also means **anything that moves on its own reads as an edit**. Three real offenders, all fixed by comparing values instead of identity or by the `ignore` list: `CurrencyInput` applies the user's last-used currency from a **mount effect**, one render after the baseline (and `FormSheet` defers its body a frame — #51 — so the child always mounts late), which made six forms prompt on open; `SaleItemsEditor` re-reports its whole cart draft from an effect (on mount **and** whenever the products list loads), so the `cart` object identity churns — compare `cart.lines.length` / `cart.total`; and `CustomerPlansEditor`'s branch-reconciliation effect nulls an out-of-branch `planId` once `plans` load, so it tracks the rows it auto-cleared and excludes them (a later deliberate pick clears the mark). Rule of thumb: only user-entered fields belong in the check — never async-loaded data, busy/submitting flags, nested-sheet open flags, or a search/filter term. For a value seeded lazily from a prop (`PaymentDetailSheet`'s `editPaid`), skip the hook entirely and compare against the source (`editMode && editPaid !== payment.amountPaid`), or merely opening edit mode counts as dirty.

56. **The customer-list badge answers TWO questions, so it needs TWO pills — and it must never infer "unpaid" from missing data** — the card originally packed everything into one badge picked by a priority chain (`mixed → overdue → paid → partial → skipped → not_due_yet → red default`), fed by six parallel `Set`s + a `Map` in `paymentSlice`, filled by **two** queries: a month-scoped one (paid / partial / skipped / not-due-yet) and a much slower full scan for overdue (`findActivePayments()` reads *every* payment, then rebuilds a grid per line per year). Three failures fall out of that shape, and only the first looks like a bug at first glance. (a) **The two queries land at different times** and the slow one outranks the fast one, so a customer with old unpaid months rendered grey "Not due yet"/"Skipped" and flipped to red a moment later — reported as "open a customer, come back, and every not-due-yet card turns unpaid". (b) **Red was the fall-through default**, so *absence* from every set — still loading, a brand-new state, a customer with no plan — all rendered as debt; every new state therefore needed its own `Set` purely to escape the default. (c) **"Overdue" and "this month" are independent facts**, so ranking either above the other always hides one: gating on load order only decided *which* truth got lost. **Fix — one fact per pill, one fetch per map:** `PaymentService.buildCustomerStatus` returns `CustomerStatus { status, overdue, planCount, notDueLineIds }` where `status` is this month alone and `overdue` is a separate boolean; `getCustomerStatuses` builds the whole `Map<customerId, CustomerStatus>` from **one** fetch; the six sets collapse to that single map; and a customer absent from it passes `status={null}`, rendering **no** payment pill rather than red. The card draws the month pill plus a red "Overdue" pill beside it, suppressing only the plain "Unpaid" pill when `overdue` is set — months are settled oldest-first (#77), so "Overdue" already means this month is unpaid. **Which pills a customer wears is decided in exactly one pure function**, `customerFlags(status)` ([customerFlags.ts](../SubsTrack/src/modules/customer/customers/utils/customerFlags.ts)), because the list's filter tabs are the same five facts: the card reads it to render, the tab filter reads it to include (`customerFlags(status).includes(activeTab)`), so a tab can never disagree with the badge on the card inside it. A second copy of the suppression rule in the filter was exactly how the old Unpaid tab drifted — it listed overdue customers the card no longer called "Unpaid". Add a pill and its tab appears with it; the styling lookup `FLAG_STYLES` is keyed by `CustomerFlag`, so the compiler demands an appearance for every new flag. Deleted along the way: `findPaymentStatusForMonth` from **both** repositories (~225 lines of SQL/JS re-implementing the grid, carrying a "must stay in sync with buildMonthGrid" warning), `findOverdueCustomerIds`, `computeCurrentMonthStatus`, the `MonthStatusSets` type, and the six hand-written set mutators (`applyPaymentStatus` / `clearPaymentStatus` / `setSkippedStatus` / …) — whose manual upkeep had already let `reset()` clear one set out of six, leaking badges into the next login. **The `partial` badge state went too**: since a partial payment reports as `"paid"` (#34), "covered but unsettled" is unreachable for a single line, so `partial` was only ever the multi-plan `mixed` case under a second name. When adding a new badge fact, add a field to `CustomerStatus` and a pill — never a new `Set` and a new rung on a priority chain.

56b. **"Paid" has to be DEFINED as "owes nothing" — a display rule can't keep it away from "Overdue"** — two pills fixed the hiding problem (#56) but left a contradiction on screen: a card could read "✓ Paid" beside "Overdue", and a three-plan customer with one clear plan and two behind read "✓ Paid" too. Both came from the same shortcut: `status` and `planCount` were computed from **this month's entry alone**, so a line whose January was unpaid but whose March was paid counted as a paid plan, `paid === total` → `"paid"`, with the backlog demoted to a second pill. Suppressing the green pill under `overdue` would only have hidden it again — the same mistake #56 exists to prevent. **Fix — count the months, not the month:** a line is settled when it has **no unpaid required month at all** (walking every year from its start), and `planCount` is `{ settled lines, lines that ever had a required month }`. `status = "paid"` then requires every line settled, which **rules `overdue` out at the source** — the two are mutually exclusive by construction, and `customerFlags` suppresses nothing but the plain "Unpaid" that "Overdue" already covers. Three consequences worth knowing: (a) **only a month that resolved to `paid`/`unpaid` was ever required** — `before_start`, `future` (including a current month held back by the billing-day rule, `isNotDueYet`) and `skipped` mean "nothing expected", so they are counted as if they did not exist, exactly as the owner specified; (b) `paid`, `skipped` and `not_due_yet` all now mean "owes nothing", so **"Not due yet + Overdue" and "Skipped + Overdue" no longer exist** — a customer with a backlog reads "Overdue" (or "N/M plans paid + Overdue"), because owing money outranks the reason this month is quiet; (c) the tally spans a line's whole history while `notDueLineIds` / `overdueLineIds` stay **this-month** facts — quick pay collects the current month, so those two must keep the current entry as their source. Under the oldest-first rules (#77, #79) "settled" and "last required month is paid" are the same thing for new data; they diverge only for legacy rows, and only the first reading can be trusted.

57. **Never audit `upsertFromServer` — the audit trail is written by the APP, not by a trigger and not by the pull** — a Postgres trigger looks like the obvious place, but it only fires when the row *reaches* Postgres, which for an offline device is at the next sync: it would stamp the sync moment and the syncing session instead of the real action and the real person, and a device that never synced would hold no history at all. So each repository writes its own row. The mirror-image trap is `upsertFromServer` ([db/dml.ts](../SubsTrack/src/core/offline/db/dml.ts)): that is the **pull** merging the server's rows, not a user action. Auditing it **loops** — pull → audit row → push → another device pulls it → another audit row — and every entry names whoever happened to be synced in, not whoever acted.

58. **The offline audit insert belongs INSIDE the caller's `write()` transaction** — use `OfflineBaseRepository.auditIn(db, input)` with the transaction's `db`, never `this.db` (which opens its own). The change and its trail must commit or roll back together; a crash between two separate writes loses the trail for a change that stuck — the one case the whole feature exists to cover. This is also why `auditIn` **does** let a failure propagate (rolling the change back is the correct outcome), while the online `BaseRepository.audit(input)` **never throws**: there is no shared transaction to protect, and a failed audit insert must not fail the user's save. The two paths therefore diverge on detaching as well — see #72.

59. **An `appendOnly` push MUST pass `ignoreDuplicates`, or one lost response wedges the table forever** — `_dirty` clears only on a successful reply, so a push that **committed on the server but lost its response** is re-sent on the next cycle and hits the unique conflict. A plain upsert resolves that with `ON CONFLICT DO UPDATE` — which an **insert-only RLS table refuses** (`audit_logs` deliberately has no UPDATE policy, #60). The row can then never succeed, and because `pushDirty` sends a table's dirty rows as **one batch**, it freezes every later audit row behind it (same batch-poisoning shape as gotcha #48). `ignoreDuplicates: true` → `ON CONFLICT DO NOTHING`, which is exactly right for an append-only log: the row is already up there.

60. **Staff can INSERT audit rows but not SELECT them — a non-admin's pull returning nothing is intended** — `audit_logs_insert` covers **every** tenant member (a staff device must be able to push its own trail), while `audit_logs_select` is **admins only** (reusing the `tenant_settings_write` role test, branch-aware via the row's own `branch_id`). There is deliberately **no UPDATE and no DELETE policy at all**: append-only from the client, only `service_role` can rewrite or purge — the same "absence of a policy = service_role only" idiom as `app_options`. The visible consequence is not a bug: a staff device's pull returns zero audit rows, so its local table only ever holds its own un-pushed ones.

61. **`occurred_at` is the client clock, `updated_at` is the server clock — never sort or display the trail by `updated_at`** — `occurred_at` is when the staff member actually acted (stamped on the device, which may have been offline for days); `updated_at` is written by the server trigger and exists only as the incremental **pull cursor**. Ordering by it would list a week-old field action as if it happened at sync time, which is precisely the evidence the feature is meant to preserve. Every read is `ORDER BY occurred_at DESC`, and the local window filter is `.gte('occurred_at', cutoff)`.

62. **The local audit trail is a 30-day window — a local count is never a total, and the window is a FALLBACK, not the default view** — `pullDays: 30` (`AUDIT_LOCAL_DAYS`) keeps the mirror small, so it can only ever answer "what happened lately". The first version made that window the native default and put the real history behind a **"Load full history"** link: an admin opening the trail to settle a dispute saw a truncated list and no reason to suspect it, and the one action that fixed it was a grey line of text under the filter chips. Every read is now server-first (#76), the window is what you get when the server can't be reached, and the note above the list says which one is on screen. Two rules survive the change: don't present a local number as "all changes", and don't hardcode a page size in an audit read — the local window pages at `OFFLINE_PAGE_SIZE` (100) while every Supabase query pages at `PAGE_SIZE` (30), which is why `hasMore` is decided by the **repository** that ran the query and not by the caller measuring the array (`auditPageSize(scope)` is gone with the scope it took).

63. **The window prune must keep `_dirty = 1` rows regardless of age** — `pruneWindowedTables(db)` deletes local rows older than the window, guarded by `_dirty = 0`. An un-pushed row is the **only copy in existence** — nothing on the server, nothing on another device — so age must never delete it (a device offline past the window would otherwise quietly destroy its own trail). It runs after each complete sync cycle **and** once at bootstrap, so a device offline for months still prunes on next start.
64. **An audit diff must compare a row against the SAME shape — a joined select on one side invents changes that never happened** — several online repositories snapshot the "before" row with a bare `select('*')` but re-read the "after" row with their **join** select (`CustomerRepository`'s `SELECT` pulls a nested `customer_plans` array, `CustomerPlanRepository`'s pulls `plans`). The diff then compares *key absent* against *array of nested rows*, so editing one scalar recorded a phantom `customer_plans` change and dumped the entire nested JSON into the trail as unreadable text — the real symptom that surfaced this: "I only changed the start date". Fixed centrally, not per call site: `ownColumns()` in [buildAuditRow.ts](../SubsTrack/src/core/audit/buildAuditRow.ts) drops every non-scalar value before diffing, because **an audit row describes ONE table's own columns** — a child's change gets its own entry from its own repository (and `describeAudit` then can't stringify an object into a label either). Don't "fix" this by switching a before-read to the join select: that just makes both sides carry children the row doesn't own. The display side is defensive too — `formatValue` renders a stray array as "N items" and an object as "(details)" rather than raw JSON.

65. **A person id is resolved for DISPLAY, never stored as a name — and "(empty) → (empty)" means a blank string met a NULL** — two separate readability faults surfaced on the same void entry. (a) `voided_by` / `remitted_by` / `received_by_user_id` / `skipped_by_user_id` / `recorded_by_user_id` hold a **user id**, and the sheet rendered the raw UUID — on a trail whose whole point is *who did this*, unusable. `formatField()` ([format.ts](../SubsTrack/src/modules/admin/audit/utils/format.ts)) resolves those through the loaded staff list, falling back to "Deleted user" rather than a UUID. Resolution happens at **read** time on purpose: a name frozen at write time goes stale on a rename, and the id must survive in the row regardless. Both now live in the per-column display registry ([valueDisplay.ts](../SubsTrack/src/modules/admin/audit/utils/valueDisplay.ts), #67) as `*.<column>` wildcard entries, which deliberately exclude **record** ids (`customer_id`, `plan_id`, …) — those identify the row the entry already names, and a deleted record has no name left to resolve to. The entry's own "Staff" row is different again: it reads `actor_username`, a snapshot stored on the row so it survives the user being deleted. (b) An optional text field submits `''` where the column holds `NULL`, so `sameValue` counted no-value → no-value as a change and the sheet showed `(empty) → (empty)` (real case: voiding a sale with a blank reason, which writes `void_reason: ''` over `NULL`). `isBlank()` in [buildAuditRow.ts](../SubsTrack/src/core/audit/buildAuditRow.ts) now treats `null`/`undefined`/`''` as one value — a *real* reason is still recorded. Also: don't label the entry's timestamp with `payments.paid_on`; `audit.occurred_at` ("When") is the table-neutral wording, since the same sheet renders customer and plan edits.

66. **A multi-record trail query must match `(table, id)` PAIRS — two `IN`s cross-match, and there is no parent link to use instead** — one entity's history can span rows (a customer plus its service lines), so `IAuditRepository.findForRecords(targets)` takes explicit `(table, recordId)` pairs. The tempting shortcut, `.in('table_name', tables).in('record_id', ids)`, is **wrong**: it accepts any combination, so a plan line's id matches under `table_name = 'customers'` and a foreign entry lands in the timeline. Both impls therefore build an OR of grouped terms — PostgREST `or('and(table_name.eq.X,record_id.eq.Y),…')`, SQLite `(table_name = ? AND record_id = ?) OR …` with flattened params. And you cannot avoid the pairs by querying a parent id: an audit row stores **only its own** table and record id, by design (`before_data`/`after_data` hold a diff, not a relationship), so the caller resolves the children it cares about. Two consequences worth knowing: **skipped months can't join a customer's timeline** this way, because a skip's id is a hash of `(customer_plan_id, billing_month)` and isn't enumerable without querying every month; and a hook taking a `targets` **array** must depend on its serialized CONTENTS, not the array identity, or an inline `[{…}]` prop re-fetches every render (`useRecordHistory` rebuilds the array from that key — an `eslint-disable react-hooks/*` would have switched React Compiler off for the file, #52). **Superseded for the CUSTOMER timeline by #75**: an entry now freezes `subject_id`, so a customer's whole trail — skips and voided payments included — is one indexed query. `findForRecords` stays for a multi-row entity that shares no customer.

67. **A raw column is not a displayed value — register the display once per column, never special-case it in the sheet** — the trail stores raw columns on purpose (evidence, not prose), so a setting change showed `UnpaidStartRule · month_start` and `customer_start_day → month_start`: correct data, unreadable to the person it was written for. The fix is a **registry** — [valueDisplay.ts](../SubsTrack/src/modules/admin/audit/utils/valueDisplay.ts), one flat table keyed `<table>.<column>`, with `*.<column>` for a column any table can carry (the five person ids, `currency_id`, `branch_id`), resolved most-specific-first: the table's own key → the wildcard → the generic `formatValue`. Four rules keep it from becoming a liability. (a) **A formatter returns `null` for anything it does not recognize**, so an unmapped enum, a new column, or a table nobody registered still renders exactly as before — never blank, never a crash. (b) **Ids resolve at READ time** (`useAuditLookups()`), never frozen as names: a frozen name goes stale on a rename, and the id must survive in the row regardless (#65). (c) **NULL means something different per column** — a null `currency_id` is USD, a null `branch_id` is "Shared" on a plan but "Unassigned" on a customer and "Tenant-wide admin" on a staff row — so `idRef` takes a `blank` label instead of falling through to a meaningless "(empty)". (d) **Some values cannot be decoded alone**: `tenant_settings.value` is a rule name under one key and a currency id under another, and an edit stores ONLY the changed column, so `key` never reached the read side at all. `CONTEXT_FIELDS` in [buildAuditRow.ts](../SubsTrack/src/core/audit/buildAuditRow.ts) copies such a column into the payload even when unchanged, **outside `changed`** so it is never rendered as a change (`AuditEntry.context` on the read side). Don't solve that by parsing the frozen `label`, and don't put a value map inside a component: the list card and the detail sheet both render the same entry, and one shared source is what keeps them from disagreeing.

68. **The WhatsApp invoice is one deep link, and its text format has two traps** — the whole feature is `openWhatsApp(phone, text)` (a `wa.me` URL through `Linking.openURL`), so it needs no native module and ships over the air. Two things bite. (a) **On web the send happens after an awaited save, so the user-gesture context is gone.** `Linking.openURL` on RNW is `window.open`, and Chrome/Safari may silently block the new tab *while `openWhatsApp` still returns `true`* — there is nothing to detect. This is why every record stays re-sendable from `PaymentDetailSheet` / `SaleDetailSheet`, where the send **is** a direct gesture; don't restructure the save path chasing it. (b) **WhatsApp markup is real markup.** Only the org name is wrapped in `*…*`, and nothing that can contain user-typed `*`, `_` or `~` (a customer name, a product name, a note) is ever wrapped. List rows must start with the literal `•` — a leading `*` or `-` is parsed as bold/italic and the message renders mangled. Both rules live in ONE file, [invoiceText.ts](../SubsTrack/src/modules/invoicing/utils/invoiceText.ts): the builders are pure and take `t` in an `InvoiceContext` (the `blockRangeLabel.ts` pattern), so the format is changed in one place and a payment receipt can never drift from a sale receipt. Also: the date uses `getDateLocale(language)` (always `en-US`) on purpose — `formatMoney` hardcodes Latin digits, so an `"ar"` date would mix numeral systems inside a single message. And a multi-line payment invoice prints **one Total per distinct currency**, never a numeric sum: each service line can carry its own currency.

69. **The pay actions RETURN the created record — don't reintroduce a `lastCreatedPayment` state field** — an invoice needs the real receipt id and `paidAt`, so `createPayment` (`Promise<Payment | null>`), `createPayments` (`Promise<Payment[]>`), `createMultiMonthPayment` (`Promise<CreateMultiMonthPaymentResult | null>` — the already-exported `{ payment, conflictMonths }` the service was returning anyway), `createMultiMonthPayments` (`Promise<{ payments, conflictMonths } | null>` — **widened from the bare `MultiMonthConflict[]`**, which no caller was reading) and `bulkPayCustomers` (`Promise<Payment[]>`) forward what the service produced instead of discarding it. That is deliberately *not* a new slice field: a `payments.lastCreated` would be a second source of truth that every caller would have to clear, and two entry points firing at once would race. Two consequences to respect: (a) **`PaymentFormSheet` still tests success with `getStore().getState().payments.error`**, not the returned record, so the tier-limit path (which returns null *and* sets `tierLimitError`) keeps behaving exactly as before — swapping it for `if (created)` would silently change that. (b) **`bulkPayCustomers` is all-or-nothing**, so `created.length` is either 0 or `requests.length`; `executePay` derives its "N failed" notice from that, and a caller must not treat a short array as a partial success.

70. **A form with two submit buttons needs ONE busy marker set before the write — and its validity gate must not include the loading flag.** A "Save & send on WhatsApp" submit is two awaited phases (the store write, then the deep link), and the first version tracked them with two booleans: the slice's `loadingCreate` plus a local `sending` set only *after* the write returned. During the save half of a WhatsApp submit `sending` was still `false`, so `loading={loadingCreate && !sending}` lit up the **primary** button — the spinner sat on a button the user never pressed. `PaymentFormSheet` / `SaleFormSheet` now hold `busyOn: "save" | "send" | null`, set **before** the write and cleared in a `finally`, and each button keys its `loading` off it (the union makes "both spinning" unrepresentable). The non-obvious half: **`canSubmit` / `submitDisabled` must be validity-only.** Both buttons feed that predicate into `disabled`, and `SendOnWhatsAppButton` renders `disabled` as `opacity-40` **and suppresses its spinner**, so leaving `!loadingCreate` in the gate greys out both buttons mid-submit and defeats the whole fix. Gate the busy state per button instead (`disabled={!canSubmit || busyOn === "save"}`). Do **not** add `busyOn` to `useDirtyForm` — busy flags are exactly the false-positive class gotcha #55 warns about.

71. **The customer on an audit card is FROZEN (`audit_logs.subject`) — this is the one id that must not resolve at read time** — the trail's whole reading order is "what record, whose, who did it", but a payment / sale / skip / service-line entry named no customer at all: `describeAudit` deliberately builds `label` from the row's **own** columns (#65), and `customer_id` is just as deliberately excluded from the read-time display registry (#67). Both halves of the obvious fix are wrong. **Resolving the id in the UI fails exactly when it matters**: `useCustomerSlice.items` is paginated (30), branch-filtered and cleared on every search, so a lookup built from it misses most customers — and a *dedicated* all-names query still renders "(deleted)" for a deleted customer, which is precisely the dispute the trail exists to settle. So `subject` is frozen at write time, like `label` and `sales.items_summary`, and it is the **deliberate exception to #65's read-time rule** (that rule protects against a stale name after a rename; here a stale name is the *correct* answer — it is what the record said when the person acted). Three things follow. (a) It costs **no extra query**: `customerAudit(customerId)` on both base classes replaced the four duplicated `branchOf` helpers and returns `{ branchId, subject }` from the one lookup those call sites were already making — never add a second query for the name. **Online, don't resolve it at the call site at all**: pass `customerId` in the audit input and let the detached `audit()` do it in the background (#72) — it fills only the fields you omitted, so a table that owns its `branch_id` (sales) just passes `branchId` and inherits the name alone. Online sale create/void get the name free from the already-joined `customers` and still pass `subject` directly. **Offline the old rule stands** — resolve one entry per distinct customer into a `Map` **before `write()` opens**, since the transaction must stay short and `auditIn` runs inside it. (b) On `customers` no caller passes a subject: `buildAuditRow` fills it from the row's own `name`, which works for an **edit** too only because it reads the full `after`/`before` row, not the diff — an edit's diff holds `name` only when the name itself changed. (c) The card and the sheet must both **drop the record label when it equals the subject**, or a customer edit prints the same name twice. Rows written before the column exists have `subject: null` and simply show no name — never "(empty)".

72. **The ONLINE audit write is detached; the OFFLINE one must never be** — the trail was on the user's critical path: every save awaited a customer lookup plus an `audit_logs` insert (two extra round-trips), and a bulk collect awaited them per row, so the spinner outlasted the work the user was actually waiting for. `BaseRepository.audit()` now returns `void` and runs its lookup + insert in the background. That is safe for exactly one reason: **the entry describes a write that has already committed**, nothing above depends on its result, and it never threw even when awaited — so detaching changes no outcome, only when it finishes. Three things to keep straight. (a) **Do not "fix" the offline path the same way.** `auditIn` is local (no network — it was never the slow part) and belongs **inside** the caller's `write()` transaction so the change and its trail commit together (#58); detaching it would both break that and run after the transaction closed. (b) **`audit()` returns `void`, not a promise** — `await this.audit(...)` is harmless but pointless, and the compiler no longer stops you writing an audit call that silently never runs, so keep the call shape uniform. (c) **A bulk path now fires one background lookup per row** rather than one per distinct customer (the per-loop `owners` maps are gone with the awaits). That is deliberate — the queries are detached, so they cost the user nothing, and a dedupe cache would have to be short-lived anyway, since the name is frozen into each row (#71) and a rename must show up in the very next entry. Don't add one back without a measured reason.

73. **A branch-aware read has TWO scopes to satisfy, and RLS only covers one of them** — the Audit Log showed every branch even with a branch picked, and the code said why in a comment: "tenant and branch scoping are enforced by the audit_logs_select RLS policy, so nothing is filtered here." That is true for a branch-**bound** user (`users.branch_id` set) and false for a tenant-wide admin (`branch_id IS NULL`), who is *supposed* to see every branch — for them RLS is not a filter at all, and the header chip is the only thing that narrows the view. The two mechanisms answer different questions: **RLS decides what a user MAY see, the picker decides what they WANT to see right now.** Satisfying only the first is what made the trail the last branch-aware list in the app without a `resolveBranchFilter` call. The fix is the standard four-part seam every other list already has — `AuditFilter.branchFilter`, `applyBranchFilter` / `branchWhere` in both repositories, `resolveBranchFilter(get().auth.user)` in the slice, and `branchFilter` in the screen's effect deps — plus one choice specific to the trail: the scope is **`shared`, not `owned`**. `audit_logs.branch_id` is denormalized and legitimately NULL for records that belong to no branch (a plan, a tenant setting, a staff member), so `owned` semantics (`branch_id = ?`) would silently hide every settings and plan change the moment an admin picked a branch. Whenever you add a branch filter to a table that stores NULL for "tenant-wide", ask which of the two it means — "unassigned" (`owned`) or "belongs to everyone" (`shared`) — because the wrong answer fails quietly, only for some rows.

74. **A debt has two dates and they are not interchangeable — group by when it was RECORDED, display what it is ABOUT** — the debt history bucketed a subscription debt under its `billing_month`, so a partial payment collected today for November 2027 opened a "NOVEMBER 2027" section above "TODAY", and today's work scattered across future headers. `DebtItem.date` is polymorphic by design (`billing_month` / `sold_at` / `incurred_at`) and for two of the three sources it happens to be both dates at once, which is exactly why the bug hid: only the months category can have a billing month years away from the moment the debt came into being. `DebtItem` therefore carries **`createdAt` as well** — `payments.paid_at`, `sales.sold_at`, `custom_debts.created_at` — and **every ordering and grouping reads `createdAt` while every card still displays `date`**. Two follow-ons. (a) `DebtService.getDebtsView` sorts on `createdAt`, and so must `DebtList` and `DebtHistorySheet`; a list that sorts on one field and groups on the other produces duplicate section headers, because `groupByMonth` only opens a new section when the key CHANGES and trusts the caller's order. (b) The history header shows the two sums **side by side** (debts red `+`, payments green `−`) instead of one net figure: a month that added $300 of debt and collected $300 nets to zero and reads identically to a month where nothing happened. `groupByMonth` still takes a single `getAmountUsd`, so the sheet passes none and computes both sums itself over `section.data` — don't widen the shared helper for one caller's two-sided total.

75. **A customer's whole trail is found by `audit_logs.subject_id`, not by listing child ids** — `findForRecords(targets)` was the only way to read more than one row's history, and it forced the caller to enumerate every child id. That works for a customer plus its service lines and breaks for everything else: **skipped-month ids are a hash of (line, month)**, so they cannot be listed without querying every month, a long-standing customer has hundreds of payments (an `or=(...)` of that many `(table,id)` pairs does not fit in a URL), and a **voided** payment is missing from `findByCustomer` — the one entry a dispute is actually about. So an entry now freezes **who it is about as an id** (`subject_id`) next to the name it already froze (`subject`), and `findForCustomer(customerId, tables)` is one indexed query. Two things this depends on: (a) `buildAuditRow` fills it from `AuditInput.customerId`, falling back to `recordId` on the `customers` table itself (the customer IS the record) — so a table that wants to appear in a customer's timeline **must pass `customerId`**, not only a pre-resolved `subject`; (b) `customerAudit()` returns `{ branchId, subject, customerId }` on **both** base repositories, which is what makes the offline call sites' `...owner` spread carry the id. It is never joined back to `customers` — only compared — so it stays correct after the customer is deleted. Sales pass a `subject` but no `customerId`, so their entries have no `subject_id`: intentional, since a sale is not part of the subscription timeline. There is **no backfill** — entries written before the column carry NULL and are absent from a customer's history, and because `subject_id` lives in the `CREATE TABLE` (not an `ALTER`), re-running `script.sql` will not add it to an existing database; reset it, or run the one `ALTER` by hand.

76. **An offline-first read of the trail is SERVER + un-pushed local, never one or the other — and the merged length must not decide `hasMore`** — the audit log is the one table where "read the mirror" is wrong in both directions. Reading **only locally** truncates the history to 30 days, which is exactly the evidence a dispute needs (#62). Reading **only the server** is just as wrong, and less obviously so: a row this device wrote is `_dirty = 1` until the next push succeeds, so it exists **nowhere else in the world** — an admin who records a payment offline, reconnects, and opens the trail before the push lands would not see the action they just took. `OfflineAuditRepository` therefore delegates to the Supabase sibling and merges its own `_dirty = 1` rows on top, de-duped by id (a row can be up there already if a push committed but lost its response, #59) and re-sorted by `occurred_at`. Four things this pulls in. (a) **Un-pushed rows join page 0 only** — they are newer than the last successful push, so they belong at the top; merging them into every page would repeat them. (b) **`hasMore` moves into the repository.** The caller used to compare a page's length against the page size, which the merge silently breaks: 30 server rows + 3 un-pushed = 33 ≠ 30, so paging stopped after the first page. The repository knows the server page length, so it answers, and `IAuditRepository` returns `{ rows, source, hasMore }` instead of a bare array. (c) **An unreachable server degrades, it does not throw.** `isOnline()` reports the *network*, not the server, and it optimistically returns `true` while connectivity is still unknown (just after boot) — so the server read is wrapped in a `try` that falls back to the local window rather than leaving an admin with an error where the trail should be. (d) **`source` is an OUTCOME the UI reports, never a scope the user picks.** The moment it becomes a choice you are back to the "Load full history" button, and to a second state field the caller has to reset. The local-clause helper is parenthesized on use (`WHERE (${clause}) AND _dirty = 1`) because `findForRecords` passes an OR chain — without the parens `AND` binds tighter and the pending query silently returns the wrong rows.

77. **Months are settled OLDEST FIRST — the rule is one pure helper, and it must read every year, not the viewed one** — a month may not be paid while an earlier month of the same service line is still unpaid, so a customer can never end up with a paid March sitting on an unpaid January. Three things make it correct instead of nearly correct. (a) **The unpaid list spans all years.** `PaymentService.unpaidBillingMonths(line, …)` walks `buildMonthGrid` from the line's start year to today (the same loop `buildCustomerStatus` uses) — the payment panel only holds ONE year's grid, so a check written against `monthGrid` would happily let a 2027 month be paid over a 2026 backlog. The slice publishes it as `unpaidMonthsByLine` alongside `monthGridsByLine`, built in the same `buildGridsFor` pass so the two can never disagree. (b) **A month inside the same write never blocks that write.** `blockingUnpaidMonths(unpaid, targetMonths)` ([utils/payOrder.ts](../SubsTrack/src/modules/customer/customer-payments/utils/payOrder.ts)) compares against the LATEST target and excludes anything in the target set, so multi-selecting Jan+Feb+Mar pays them in one go while tapping Mar alone is refused, and a multi-month block (whose `targetMonths` is every month it covers) is judged as the unit it is. Passing only the tapped month would have blocked every legitimate backlog batch. (c) **Two layers, one implementation.** `PaymentService.assertPayableInOrder` runs inside all four payment slice create actions (so nothing can write around it), and the UI gates ahead of it — cell tap, quick-pay menu item, grid multi-select, the `?quickPay=1` deep link, an amber banner in `PaymentFormSheet`, and customer-list quick pay via the new `CustomerStatus.overdueLineIds`. The list needed a **per-line** field: the existing `overdue` flag is customer-wide, so a two-plan customer with one clean plan would have had its good plan blocked too. Skipped and partially-paid months are not `"unpaid"`, so neither ever blocks (a partial payment is a debt, not an open month). `lineUnpaidMonths` is declared next to `grid` — above the quick-pay effect — because it is in that effect's dependency array and a `const` referenced from a dep array is evaluated during render (TDZ if declared lower down).

78. **A multiline `TextInput` inside a scrollable must NOT scroll its own text — and on Android `scrollEnabled` is NOT how you stop it** — with the default settings a multiline box swallows the vertical drag: the finger is on the notes field, the field scrolls its own two lines, and the page (or the Gorhom sheet body) under it stands still. The mechanic is in `ReactEditText.onTouchEvent`: on ACTION_DOWN it calls `requestDisallowInterceptTouchEvent(true)` on its parent, and it only lets go on the first ACTION_MOVE **if all four `canScroll*` checks are false**. So the box keeps the gesture whenever it has *anything* left to scroll, and `View.canScrollVertically` needs only a **2px** overflow to say yes — which a custom font plus a Tailwind `line-height` produce easily, and which is exactly the "the text moved a little and the page didn't" report. Three consequences for the shared [Input](../SubsTrack/src/shared/components/Input.tsx): (a) `scrollEnabled={false}` (defaulted whenever `multiline` is set and the caller passed no value) is **iOS-only** — real, but it fixes nothing on Android; (b) on Android the box is therefore **pinned to the height it just reported** through `onContentSizeChange` plus a few px of `GROW_SLACK`, which is the only way to be certain there is nothing left to scroll (`contentSize.height` already includes the padding, and the pinned height is applied LAST so a caller's `minHeight` still wins while its `height` does not); (c) **`numberOfLines` is dropped** along with the inner scroll — on Android it maps to `setLines(n)`, pinning an exact height and bringing the scroll (and clipping) straight back. Passing `scrollEnabled` explicitly opts out of all of it: the developer import box does, since a pasted export can be thousands of lines and growing it would blow up the page (it pairs the opt-out with a `maxHeight`). The five hand-rolled void-reason `TextInput`s are deliberately untouched — they live inside `ConfirmDialog`, which has no scroll view to steal from, and letting them grow would push the dialog's buttons off screen. **Known remainder:** a SINGLE-line field is horizontally scrolling on Android, so one whose text is wider than the box holds the drag the same way. Nothing shipped fixes it — the only cure is covering the unfocused field with a transparent tap-shield, which costs tap-to-place-the-caret on every field in the app. Do not add it without deciding that trade deliberately.

79. **"Pay the oldest month first" is not one rule but an INVARIANT with three doors, and closing only the pay door leaves the other two wide open** — the invariant is *a paid month never sits on top of an unpaid one*, because that is what makes a customer card readable ("✓ Paid" beside "Overdue" is a contradiction staff cannot act on) and what keeps collection in order. #77 shipped the pay door. The other two were found by asking why a live customer showed exactly that badge pair: (a) **void** had no order guard at all, so undoing January while February stayed paid recreated the state instantly — and `runBulkVoid` called nothing while its sibling `runBulkPay` called `payOrderBlocker`, which is what made the asymmetry easy to miss; (b) **a line's start_date was freely editable with payments recorded**, so dragging it back a year invented a year of unpaid months *behind* paid ones (and pushing it forward hid months whose payment rows still existed, turning them into `before_start` cells with money attached). The fix mirrors #77 door for door: `blockingPaidMonths(paidMonths, targetMonths)` is the exact reflection of `blockingUnpaidMonths` (paid months **after the EARLIEST** target, excluding the write's own months, newest first — so voiding a whole tail together passes while cherry-picking an older month out of it does not), and `assertVoidableInOrder` sits **inside** `voidPayment` / `voidPayments` / `voidCurrentMonth`. Four things that are easy to get wrong here: (1) **the guard must resolve its own rows** (`repository.findByIds`, a new method on both payment repositories) rather than take them from the caller — the Transactions → Payments tab voids a mixed selection across many customers and never loads a grid, so a slice-level check could not reach it; (2) **the target months come off the PAYMENT, not the cell** (`coveredBillingMonths(payment.billingMonth, payment.durationMonths)`) — a multi-month block's secondary cell has its own month, not the block's start, and a block is always voided whole; (3) **the check spans every year**, so the panel needs `paidMonthsByLine` next to `unpaidMonthsByLine` (both built in the one `buildGridsFor` pass, both fed by payments rather than the viewed grid) — Dec 2026 must be blocked by Jan 2027; (4) **a partially-paid later month still blocks** (it is real money) while a zero-`amount_paid` slot never does. For the start date the guard is `CustomerPlanService.assertStartDatesUnlocked`, run at the TOP of `syncLines` before any write, and only for lines whose date actually changed — so the extra query is skipped on the ordinary save. It needs its own probe, `findPaidLineIds(customerId)` (non-voided, `amount_paid > 0`, one query for the whole form): **do not reuse `countPayments`** for this, which counts voided rows on purpose (a line whose payments were all voided still has history a hard delete would take with it, but its start date is safe to move). **Still open by design:** unskipping an old month can put an unpaid month behind a paid one — the owner chose to leave that alone. Such a line (and any legacy row predating these guards) is still real data, but it can no longer produce a "✓ Paid + Overdue" card: "paid" now means "owes nothing" (#56b), so it reads "Overdue" — or "N/M plans paid + Overdue" when the customer's other plans are clear.

80. **A receipt for an EXISTING selection is not the same job as a receipt for a write, and three things it must not inherit** — "pay & send" builds its message from the rows it just created, which are by construction one customer, one moment, one row per bullet. Re-sending months/sales that were already collected breaks all three assumptions. (a) **Build the rows from PAYMENTS, not from selected cells.** A multi-month block fills several month cells that all point at the *same* `payments` row, so mapping the selection straight to bullets bills a 3-month block three times and prints its receipt id three times; `CustomerPaymentPanel` de-dupes with a `Map` keyed on `payment.id` (the same dedupe `runBulkVoid` already did for ids) before handing them to the builder. (b) **A multi-row message can no longer claim one "Paid on".** Months picked from a grid or the payments list were collected on different days, so `buildPaymentInvoiceText` compares the formatted dates and only keeps the header row when they all match — otherwise the date moves onto each bullet. This is why the quick-pay message is byte-identical to before (one instant → one date) while a historical selection dates every line. Both multi-row builders also **sort oldest-first** (`billingMonth` / `soldAt`), because a list hands over its selection newest-first and a receipt reads as a statement; the sort is stable, so several lines of the *same* month keep their plan order. (c) **One message has one recipient.** The month grid is already per-customer, but a sales/payments list selection can span customers, or hold a walk-in sale with no customer at all — `resolveInvoiceRecipient` (pure, in `invoicing/utils/`) collapses the rows to a single `{name, phone}` or names the reason (`mixed` / `no_customer` / `no_phone`), and `useSendInvoice.resolveRecipient` turns that reason into a dialog. On those lists the action stays **visible and explains itself on press** (the `showPayOrderBlocked` pattern) rather than appearing and disappearing as rows are ticked; only the fixed-customer grid toolbar keeps the older "hide it when there is no number" rule, because there the answer cannot change mid-selection. Voided rows are filtered out **before** any of this — a cancelled receipt is not a receipt (#4 of the QA invariants), and on the payments list the *same* live-rows array feeds both the send and the void action.
