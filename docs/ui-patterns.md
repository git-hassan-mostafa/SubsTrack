# UI Patterns — sheets, cards, headers, styling

Moved out of CLAUDE.md. Read before touching a bottom sheet, a list card,
`PageHeader`, `ActionMenu`, or the responsive/web layout.

## Styling

- NativeWind (Tailwind) classnames on all components. Design tokens in `src/shared/constants/colors.ts`.
- Custom `Text` component handles Cairo font for Arabic, system font for English.
- **Weight is a PROP, never a class.** `fontWeight="Medium" | "SemiBold" | "Bold"` on `Text` swaps the Cairo **face** (`Cairo-Medium` / `Cairo-SemiBold` / `Cairo-Bold`), and each face is registered as its OWN font family in `app/_layout.tsx`. A Tailwind `font-semibold` / `font-bold` / `font-medium` class sets only a numeric weight on the plain `Cairo` family, which can never reach those faces — the platform then SYNTHESIZES a fake bold from the regular outline instead of drawing the designed one (heavier, muddier, and worst on Arabic). 144 call sites carried the class; they are props now and **zero weight classes remain in `src`** — a grep for `font-semibold` is the check. `Chip` carries its `md` weight the same way.
- RTL support via `I18nManager`; language change triggers a full app reload (see gotcha #5).
- Keyboard avoidance uses `react-native-keyboard-controller`, **never** RN's built-in `KeyboardAvoidingView` (see gotcha #39).
- Entity list rows (customers, users, plans, branches, currencies, products, sales) share one shell: `<EntityCard>` (`src/shared/components/EntityCard.tsx`). It owns the common chrome — wrapper styling, the tap/long-press selection handshake, the icon-tile↔checkbox swap, and the trailing 3-dot menu — so each card only passes its icon (`icon`/`iconColor`/`iconBgClassName`), the `on*` callbacks, optional `dimmed`/`menuLoading`, and its body as children. Build new list cards on top of it; don't re-hand-roll the card skeleton. It also takes `disabled` (a row nobody may act on must not flash under a press) and it is what the **audit trail** rows and the **wallet detail** rows use now — both had hand-rolled the skeleton with their own padding.
- **One card surface, one constant.** `CARD_SURFACE` in `src/shared/constants/surfaces.ts` (`bg-white border border-gray-100 rounded-2xl`) is the white block every card, panel and section sits in — 22 call sites across sheets, settings, dashboard, reports and stat tiles had retyped it, drifting to `py-2`/`py-3`/`p-4`/`p-5` and, in the deleted `MetricCard`, to a different border shade AND radius. It is a **string, not a component**, because a `PressableOpacity` and an `Animated.View` need the same surface as a `View`; padding, margins and `overflow-hidden` stay with the caller, since a list row and a settings group legitimately differ. `CARD_SURFACE_DIMMED` is the switched-off variant — a second constant rather than an appended `border-gray-200`, because two conflicting border classes in one string have no defined winner without tailwind-merge. Dialogs (`ConfirmDialog`, `UpgradePromptModal`), inset tiles (`PlanLineCard`, `RemovePlanChoice`) and the selectable `TierCard` are NOT this surface and keep their own.
- **A card’s chips come from ONE colour table, not per call site.** `TONE_CLASSES` in `src/shared/components/Chip.tsx` maps `tone` → the tinted pair — `emerald` cash/paid, `amber` partial or warning, `red` unpaid/overdue/voided, `orange` money that is real but lost (written-off, debt), `sky` not-due-yet, `slate` neutral (skipped, inactive, counts), `indigo` plan/stock, `teal` the bill kind on the debts side, `violet` manual — so the same fact wears the same colour on every screen. `Chip` has **no `className` prop**: a new colour means a new tone, and spacing goes on a wrapping `View`. Meaning → tone stays with the domain (`kindStyle.ts`’s `chipTone`, `DebtItemCard`’s `KIND_STYLE`, `CustomerCard`’s `FLAG_STYLES`). `size="sm"` is the card chip (uppercase 10px); `size="md"` is the bigger rounded badge a detail sheet’s hero row wears (it replaced `CollectionSplitSheet`’s private `Pill`). Card chips sit at the **bottom of the card body** — `mt-1 flex-row flex-wrap items-center gap-1`, never in a floating row above the card; `CustomerCard` keeps `min-h-[19px]` there because its statuses arrive after the list has painted, and the row must not resize under the user.
- **A card never types a colour, a size or a weight — it picks a ROLE.** Four primitives in `src/shared/components/CardText.tsx` own the whole ladder: `CardTitle` (`text-base` semibold gray-900, the row’s name), `CardSubtitle` (`text-xs` gray-500, what the row IS), `CardMeta` (`text-[11px]` gray-400 — when, who, or a figure’s unit) and `CardAmount` (`text-base` Bold, `tone="default" | "muted" | "danger"` — muted is a voided row, danger an unpaid one). Their `className` prop is **layout only** (`flex-1`, `mt-0.5`, `shrink`); a colour or size in there is a bug. That killed three different subtitle greys (400/500/700), four text sizes for the same job and three amount styles. **The app has ONE neutral ramp: `gray`.** `slate` was swept out of `src` entirely (it was the ledger + debts corner) and the neutral chip tone is `gray` — `COLORS` in `colors.ts` is a gray ramp, so a second ramp could only ever drift from it.
- Web/desktop width is capped via `<ResponsiveContainer>` (`src/shared/components/ResponsiveContainer.tsx`) — wraps each screen's body (and each page-sheet form) in a centered, max-width column. It's a no-op on phones (always narrower than the cap), so phone layout is unaffected; it only kicks in on wide viewports. Centered dialogs (`ConfirmDialog`, `UpgradePromptModal`) cap themselves inline with a `max-w-*` class instead. Bottom sheets cap to the **same 768px column on web** — `AppBottomSheet` sets `width` + auto side margins on Gorhom's hosting container (see gotcha #45); native sheets stay edge-to-edge.
- All sheets are `@gorhom/bottom-sheet` (v5), built on one core: `<AppBottomSheet>` (`src/shared/components/AppBottomSheet.tsx`) wraps a Gorhom `BottomSheetModal` (rendered via the `BottomSheetModalProvider` at [app/\_layout.tsx](SubsTrack/app/_layout.tsx)) and bridges the app's declarative `visible`/`onDismiss` to Gorhom's imperative `present()`/`dismiss()`. Gorhom provides drag-down / backdrop-tap close for free — but **drag is native-only**: `SHEET_DRAG_ENABLED` turns off both pan gestures on web, where a drag-close ate the next click (gotcha #46), so a web sheet closes by its header button or the backdrop; **Android Back is wired by the app** — `useAndroidBackDismiss`, every variant, because Gorhom v5 ships no `BackHandler` of its own and hardware Back must never reach the router while a sheet is open. **On web nothing listens to browser Back** — it always navigates, whatever is open; closing a sheet from a `popstate` handler left the page dead to clicks (gotcha #44). Every sheet passes `enableContentPanningGesture={false}` so its body scrolls normally, and `android_keyboardInputMode` is `adjustPan` (never `adjustResize` — the app is edge-to-edge, so the window never shrinks). **No native rebuild was needed** — it rides on the already-installed reanimated + gesture-handler. Two public wrappers:
  - `<BottomSheetScaffold>` (`variant="auto"`, content-height) — transient tap-outside popups: `Dropdown`/`DropdownModal`, `DatePickerInput`, `CurrencyInput`, `AsyncEntityPicker`, `ActionMenu`. Closes by tapping the backdrop — **this is the one kind of sheet that does**, see gotcha #151.
  - **Every sheet header dismiss says "Close" (`common.close`), never "Cancel".** It only closes the sheet — an unsaved form is caught by `FormSheet`s `dirty` guard, not by the word on the button — so `FormSheet` hard-codes `common.close` and takes **no** `dismissLabel` prop, and `Dropdown` / `CurrencyInput` / `AsyncEntityPicker` / `DatePickerInput` match it. `common.cancel` is left to `ConfirmDialog` (declining an action) and to an in-body form that backs out of a mode without closing its sheet (the sale receipt void-reason form).
  - `<FormSheet>` (`src/shared/components/FormSheet.tsx`, `variant="full"` ≈ 92% snap) — every form / detail sheet, owning the shared chrome (Gorhom handle + header of title + one dismiss action + a `BottomSheetScrollView` body in `ResponsiveContainer`). **Replaced the deleted `SheetModal`.** **A backdrop tap does NOT close it** (`dismissOnBackdropPress={false}`) — a form is a page, not a popup, and an empty form is not `dirty` so the discard guard could not catch the stray tap; it closes by the header Close button, Android Back, or a drag down by the handle / `SheetDragArea` header. Gotcha #151. Sheets with a non-standard body (`DebtHistorySheet`, `DebtorDetailSheet`, the Wallets collector sheet) build on `<AppBottomSheet variant="full">` directly. A tap low in the body can pull the form back into view through `FormSheet`’s **`scrollRef`** — the sheet fills it with its body scroll, so the caller writes `scrollBody.current?.(0)` to go back to the top. A **ref, not a context**, on purpose: the component that renders the sheet is the provider’s _parent_, so a scroll context published inside `FormSheet` (the way `AppBottomSheet` hands the guarded dismiss to `FormSheetBody`) can only be read further down the body — every real caller silently got the no-op, which is exactly how the stock sheet’s scroll was dead. The stock sheet’s “Edit entry” uses it, because the fields it fills sit far above the history row that was tapped. See gotcha #102. **A detail sheet's secondary actions go in the HEADER, not down its body** — `FormSheet` takes `menuActions?: ActionMenuItem[]` and draws a 3-dot button beside the dismiss action, opening the app's own `ActionMenu`; the body keeps only the **one** full-width action the sheet exists for (a receipt is opened to send it, a bill to collect it) while edit / history / void become labelled, colour-coded menu rows. The sale receipt had grown to **four** stacked identical bars with a destructive void as the last one, and `BillSheet` to two. Two rules: the list is **frozen when the menu opens** (`openActions`), because `ActionMenu` dismisses before it calls `onPress` and an action that removes itself from the array — the receipt's void, which swaps the menu for a reason form — would otherwise re-render or unmount the still-animating menu and wedge Gorhom's present/dismiss bridge; and a form the menu reveals must be scrolled **into view** via `scrollRef`, since the body can be scrolled anywhere when the header is tapped. A **form's** footer is a different pattern and keeps its stacked destructive action under Save (`UserFormSheet`). See gotcha #131.
    **The body renders one frame after the chrome** (`useAfterFirstFrame`) so the slide-up isn't blocked by the form's own render — Gorhom can't start animating until native has laid the sheet out, and that can't happen while JS is rendering. Only valid for FIXED-snap sheets; never defer a content-sized `auto` body. Always-mounted sheets must pass their visibility. See gotcha #51.
  - **Sheet headers are a second drag handle.** `<SheetDragArea>` (`src/shared/components/SheetDragArea.tsx`) wraps a header row and re-attaches Gorhom's **handle** pan gesture to it, so the sheet drags (and pans down to close) from the whole title bar instead of only the thin grey handle. **On web it renders a plain `View`** — it builds its own `Gesture.Pan()`, so Gorhom's `enableHandlePanningGesture={false}` does not reach it and it has to opt out itself (gotcha #46). Content panning stays off app-wide (it freezes bodies — gotcha #45), and the header holds no scrollable, so nothing is stolen from a list. Already applied to `FormSheet`, `DropdownModal`, `CurrencyInput`, `DatePickerInput`, `AsyncEntityPicker`, and the four sheets built on `AppBottomSheet` directly. Use it on **headers only** — never around a list, since the handle gesture ignores scroll offset. A body with **no** scrollable is the exception: `ActionMenu` wraps its whole menu (title + rows) and passes `activationDistance={12}` so a sloppy tap still presses the row.
  - **A confirm whose work takes time spins on its own button — pass `onConfirm`, don't await the `confirm()` result.** `ConfirmDialog` already shows an `ActivityIndicator` on the confirm button and disables both buttons whenever its `onConfirm` returns a promise; the global `confirm()` seam simply never gave it one, because `GlobalConfirmDialog` resolved and closed in the same tick (`settle(true)`). So the classic `const ok = await confirm({…}); if (!ok) return; await write();` shape closes the dialog _instantly_ and does the work invisibly behind the screen — no feedback, and the row is still there for a moment. Hand the work to the dialog instead: `await confirm({ …, onConfirm: async () => { await write(); } })`. The store keeps the callback OUTSIDE its immer state (a module-level `pendingOnConfirm`, exactly like `pendingContent` — a function is not state and immer must not draft it), `GlobalConfirmDialog` awaits it and calls `settle(true)` in a `finally`, so the dialog stays open and spinning until the write settles and closes even if it throws. Two consequences. (a) **The returned boolean stops being the interesting value** — the caller no longer branches on it, so a cancel is simply "the work never ran". (b) **The work must not throw past the dialog**: the ledger slice's async actions already catch into `error` state (§1.2 rule 10), which is why these call sites are safe; a raw repository call would need its own try/catch. The plain `await confirm()` shape is still correct for a confirm followed by something instant (navigating, clearing a field) — see gotcha #144.
  - **Closing a dirty form asks to discard — wired once, not per form.** `AppBottomSheet` takes a `dirty` prop and routes **every** close path (header button, Android Back, drag-down) through `useUnsavedChangesGuard`, which awaits the global `confirm()` dialog. A form only reports whether it has been edited: `useDirtyForm(form)` (or `useDirtyForm({ a, b }, ["ignoreKey"])`) diffs against the first render's values, and `FormSheet`/`AppBottomSheet` take it from there. Include **only user-entered fields** — async-loaded data, busy flags, nested-sheet open flags and search terms cause false prompts, and so does any field a child seeds after mount (`CurrencyInput`'s last-used currency, `SaleItemsEditor`'s cart object). Read gotchas #54 / #55 before touching the guard, the back hooks, or a dirty check. The guard lives in Shared, so the web `FormDialog` asks through the same hook and the same confirm dialog. QA: [QA/unsaved-changes.md](QA/unsaved-changes.md).
  - **Text inputs inside a sheet must be `BottomSheetTextInput`** (that's what makes the sheet lift/shrink for the keyboard) — `Input`/`CurrencyInput` swap automatically via `AppTextInput`. Fixed-snap bodies (`FormSheet` / `variant="full"` / `auto scrollable`) can be plain or Gorhom lists, and dual-context bodies take their scroll component as a **prop** (`WalletDetailView`’s `Scroll`); a **content-sized (`auto`) body must be a PLAIN RN list** — a Gorhom scrollable overwrites the sheet's measured content height, so the sheet opens too short and clips its last rows (gotcha #47). **A list that PAGES (`onEndReached`) inside a sheet must be Gorhom's** (`BottomSheetSectionList` / `BottomSheetFlatList`): the sheet owns the scroll container, so a plain RN list never learns where it is scrolled, reports "at the end" from the first frame and pages itself to the bottom with nobody scrolling — which is why `CollectionsPanel` swaps its list on `inSheet` (the two lists' generics do not unify, hence the cast there). `AppTextInput` asks Gorhom itself via `useBottomSheetInternal(true)` — the app keeps no `InsideBottomSheetContext`. **Confirmations / message dialogs (`ConfirmDialog`, `UpgradePromptModal`) stay CENTERED** RN `Modal`s — not sheets. Build new pickers on `BottomSheetScaffold`, new forms on `FormSheet`. See gotchas #44 / #45 / #47.
  - **A text field owns the text being typed — never wire `value` straight to form or store state.** `Input`, `SearchTextBox` and `CurrencyInput` keep the typed text in `useTextField` (`shared/hooks/useTextField.ts`) and read the `value` prop as an instruction: a value the field is still waiting to hear back is refused as a late echo, anything else (prefill, Clear button, "full amount" chip, +/- stepper) is adopted. A `value` that lags the keystroke by ONE render is what lost letters and threw the caret to the end of the word. A numeric owner that echoes lossily passes `expectedEcho`; a character filter passes `sanitize` — never sanitize in the owner's setter. Read gotcha #134 before adding a field or touching one.
- `<PageHeader>` (`src/shared/components/PageHeader.tsx`) is on every screen and carries a top-right **3-dot quick-actions menu** — app-wide shortcuts (Collect money / Add customer / Record sale / Add custom debt / Add expense + Batch restock — admin-only / Money received). It's a UI-only global-store seam mirroring `confirm`: the menu flips the generic `ui` slice (`src/state/slices/ui/`, the home for ephemeral cross-screen UI state — distinct from the persisted `uiPrefStore`) and the sheets are hosted once by `QuickActionSheets` (`src/modules/quick-actions/`) in `app/(app)/_layout.tsx`. "Money received" opens `CollectionsHistorySheet` (the full money-in list) and "Collect money" opens `CollectQuickActionSheet` (pick a customer, the waterfall does the rest). Detail in [docs/features.md](docs/features.md) → The Ledger / Transactions Hub.
  - **Settings is a bottom tab again** — the last one in `app/(app)/(tabs)/_layout.tsx`, visible to every role (no `href` gate, unlike home / reports / admin). The header gear (`SettingsButton`) is **gone**, so `PageHeader`'s `hideQuickActions` now suppresses the 3-dot menu only, `SettingsScreen` has no back chevron of its own (it is a tab root — Back is the tab router's job, see gotcha #93), and the dashboard's hand-rolled header mounts `<QuickActionsMenuButton>` alone.
  - **`ActionMenu` always draws a header row with a ✕ on the right**, even when the caller passes no `title` (the title side collapses to a spacer). Tapping the backdrop or dragging down still closes it; the ✕ is there because the menu can cover the whole screen bottom and a non-technical user looks for a button, not a gesture. It sits inside the same `SheetDragArea`, so it is a `PressableOpacity` and the 12pt pan threshold keeps the tap a tap.
  - **`ActionMenu` colours its icons from ONE table, not per call site.** `ICON_COLORS` in `ActionMenu.tsx` maps the Ionicons glyph → colour (trash/void = danger, cash = success, edit/open = primary, flash/refresh/pause = warning, receipt/document = sky, cube = teal, time = violet, skip = slate, whatsapp = brand green), so the same mark means the same thing in every menu with no caller change. `destructive` still wins, `iconColor` is the per-item escape hatch, `iconBadge` inherits the resolved colour, and a `renderIcon` glyph owns its own. Labels stay uncoloured. The accent tokens (`sky`/`teal`/`violet`/`slate`/`whatsapp`) live in `colors.ts` and are for icons, not surfaces.
  - **Row order is a BAND, never a hand-written position.** `sortActions()` (`Shared/src/shared/lib/actionOrder.ts`) stable-sorts every action list by one table — `open` → `money` → `create` → `send` → `manage` → `history` → `status` → `danger` — so a menu reads the same on every screen: what you came to do first, the trail second-to-last, the red block at the bottom with `delete`/`void` final. `ActionMenu`, `SelectionBar`, `InlineSelectionToolbar` and `PageHeader`s `iconActions` all sort, so a call site declares `group` and stops caring where it pushed the item; within one band the caller's own order is kept, which is why an untagged pair (the export sheet's "this view" / "everything") stays as written. An untagged row lands with `manage`, or with `danger` when it is `destructive` — so a red row can never surface above History even if someone forgets the tag. **History is the last SAFE row, not the last row**: putting it under Delete would sit a harmless action where the finger expects the dangerous one. Locked by `tests/suites/actionOrder.test.ts`.
- **Scrollbars are styled in ONE file**, `Shared/src/shared/styles/scrollbars.css`, imported by `Web/src/main.tsx` and `Portal/src/main.tsx`: a 10px bar with a 6px rounded gray-300 thumb (gray-400 on hover), clear track, no arrow buttons. It overlays nothing and changes no layout — it is only narrower than the 17px Windows default. Chromium/Safari use `::-webkit-scrollbar`; Firefox gets `scrollbar-width: thin` through `@supports not selector(::-webkit-scrollbar)`, because Chrome 121+ drops every `::-webkit-scrollbar` rule on an element that sets the standard properties. A scroller hidden with `scrollbar-width: none` (MUI scrollable `Tabs`) still stays hidden. The phone app is not touched (native draws its own indicator).

## Web tables (`Web/`)

One component, `DataTable` ([DataTable.tsx](Web/src/shared/table/DataTable.tsx)), for every list; [BranchesPage.tsx](Web/src/modules/admin/branches/BranchesPage.tsx) is the reference. QA: [QA/web/branches.md](QA/web/branches.md).

- **Server paging only.** The table gets one page of `rows` and the filtered `total` from a paged store (`Web/src/state/createPagedStore.ts`). Page sizes 25 / 50 / 100 (the free Data Grid's cap is 100). Column sorting, the column menu, filters, the column picker and column resizing are all off: the order is the server's, and a client sort over one page would lie.
- **Toolbar**: `SearchField` (owns the typed text, sends it after a 300 ms pause) · the page's filter controls · the Refresh icon · the CSV icon · `toolbarActions` (a page's extra button, e.g. Products → "Restock several") · the "Add" button.
- **Freshness**: the store keeps the query AND its rows, so opening a page again reads nothing — `open(branch?)` reads only on the first open or when the header branch changed. The Refresh icon (`onReload`, the same handler as the error banner's Try again) reads the page again; changes made on other devices show only then. Customers, Audit Log and Money received pass `{ rereadOnOpen: true }`, because every screen and device changes them. After a write through the Shared slice, an **edit or status change patches** the row the slice returned (`patchRow`) — it stays where it is, even when it no longer matches the filter or sort, until the next read; an **add or delete re-reads** the page, because only the server knows where a new row sorts and which row slides up to fill a gap.
- **Row actions**: a ⋮ menu per row (`RowActionsMenu`), items are `TableAction`s ordered by Shared `sortActions` — the same bands as the phone's `ActionMenu`. The record's name opens Edit (a link button in its cell); a plain row click does nothing.
- **Selection**: checkboxes only when the page passes `bulkActions`; ticking rows swaps the toolbar for the bulk bar (count, actions, X). Header tick = this page only. A new page of rows (page change, search, any write) drops the selection.
- **Empty states**: "no data yet" (title, hint, the Add button) vs "no results" (hint + Clear filters) — the page says which through `filtered`. Nothing shows until the first load finished (`loaded`), so the empty message never flashes.
- **Errors**: a failed read shows an `ErrorBanner` with **Try again**; a failed write shows the slice's error above the table (or inside the form dialog while it is open).
- **CSV**: admins only, like the phone. Rows go through Shared `toExportTable()` (the phone's export uses the same helper). With more rows than the page, the icon asks "Only this page" or "All matching rows"; "all" reads the list to its end with Shared `readAllPages()` in pages of 500.
- **History**: `useRecordHistoryAction(table)` gives the row action and the dialog (Shared `useRecordHistory` + the audit sentence builder); non-admins see "Admins only". Clicking an entry opens `AuditEntryDialog` (the sentence, who / when, every field old → new, or the whole row for a create/delete) — the Audit Log page opens the same dialog.
- **Striped rows**: every grid (`DataTable` and `LocalTable`) shades every second row of the page (`rowClassName` in `gridBase.ts`, `background.default`); `rowTone` (muted / highlighted) still wins.
- **Tables inside a dialog** (stock history, record history, an audit entry's changes, the payments on a bill, the bills a payment paid): `LocalTable` ([LocalTable.tsx](Web/src/shared/table/LocalTable.tsx)) — the SAME Data Grid look as `DataTable` (shared `gridBase.ts` + `actionsColumn.tsx`) for rows already in memory: no toolbar, a footer only past 25 rows, `rowTone` greys a voided row or highlights the one being edited; an optional `selection` (`ids`, `onChange`, `isSelectable`) adds checkboxes whose picked set the CALLER owns, so it can widen a pick (the months table moves a bundle whole) (`DataTable` takes the same `rowTone`; Money received greys its voided rows). A table whose cells hold INPUTS or tick boxes (plans on the customer form, Batch Restock, the collect bills) stays a plain MUI `Table` — the grid's cell keyboard handling fights typing. **Never a phone-style stacked `List`** on the web: wide dialogs lay facts side by side (figure beside `InfoRows`, fields in one row, a payment panel beside the bills).
- **Rows that grow**: pass `autoRowHeight` only when a cell holds wrapping text (the Audit Log sentence); every other list keeps the fixed row height — a two-line `MoneyText` fits it. Auto height makes the grid MEASURE every row again whenever it gets a new `columns` array.
- **Keep the grid's props stable** — the web has no React Compiler, so opening a dialog re-renders the page. Build `columns` in `useMemo` and pass `rowActions` / `bulkActions` / `rowLabel` / `rowBusy` / `rowTone` as `useCallback`s (or module functions); otherwise every dialog open hands the grid new columns and it rebuilds all rows (Money received felt slow to open a payment). `useBranchColumn` is memoized for this.
- **Two submit buttons in a form**: `FormDialog`'s `secondarySubmit` (label + handler) draws an outlined button beside Save that goes through the same saving spinner (Update your limits → "Send request + WhatsApp"). wa.me links come from Shared `whatsAppChatUrl()`; the web opens them in a new tab with `Web/src/shared/lib/openWhatsApp.ts`.
- **A settings page** (Organization Settings) is not a table: `SettingsSection` cards in one column, each control saving on pick like the phone.
- **Branch-scoped lists** (plans, services, products, users, later customers…): the page calls `open(useEffectiveBranchFilter())` (an unscoped list calls `open()`). The store keeps that branch in `query.branch` (never a user filter — Clear filters keeps it), sends it to `findPage`, and goes back to page 1 when the header branch changes. `useBranchColumn(nullLabel)` adds a Branch column only when the tenant has 2+ active branches.
- **Reuse per list**: `RowLink` (the name cell that opens Edit), `ActiveFilterSelect` + `activeStatusColumn` (every list with an `active` flag; the query type is Shared `ActiveFilter`, the repositories use `applyActiveFilter` / `activeWhere`), `MoneyText` + `useMoneyPair()` (an amount in its OWN currency with "≈" the display currency under it; money columns are right-aligned). A new record's branch comes from Shared `defaultNewBranchId()` (phone forms too); the form's branch field is `BranchPicker`, hidden like the phone's.
- **Search over several columns on a shared-branch table** (users: username, full name, phone): Supabase `findPage` uses `BaseRepository.applyBranchAndSearch()`, which folds the branch `or()` and the search into ONE `or(and(or(…),or(…)))` — a query never gets two `or()`s. A single-column search (services, plans, products) stays a plain `ilike`.
- **Quick actions**: a header icon calls Shared `useUiStore().openQuickAction(key)`; `app/layout/QuickActionDialogs.tsx` (mounted once in `AppFrame`) renders the dialog for that key on any page. A dialog that writes rows a table shows calls that table store's `reloadXIfLoaded()` when it saves (Batch Restock → `reloadProductsTableIfLoaded`). The page can open the same dialog through the same key.
- **Customers** ([CustomersPage.tsx](Web/src/modules/customer/customers/CustomersPage.tsx), QA [QA/web/customers.md](QA/web/customers.md)): the only list NOT on `findPage` — each page comes from the `customer-status` edge function, which also returns every tab's count; `createPagedStoreWithMeta` keeps those counts beside the rows (`meta`) so the tab row reads "Overdue (12)". The tab is a filter (`filters.tab`), so a new tab goes back to page 1 and Clear filters returns to Active. Status pills come from Shared `customerPills()` (the phone card uses the same rule); debt has its own right-aligned column. A pill cell can wrap, so the page passes `autoRowHeight`. The CSV exports the plain `Customer` records (`exportConfig.record`), the same columns as the phone. History is the WHOLE customer story (`CustomerHistoryDialog`: profile, lines, month payments), not one row. The form (`CustomerFormDialog`) runs on Shared `useCustomerForm`; any later page that adds a customer (sale form, quick action) opens this dialog — never a second form.
- **Money row actions** (Customers): Quick pay, Pay & send on WhatsApp, Collect money, and Quick pay in the bulk bar for EVERY role (the phone lets every role select; admin-only items are filtered per action). The rules are Shared [quickPay.ts](Shared/src/modules/customer/customers/utils/quickPay.ts) + [useQuickPay.ts](Shared/src/modules/customer/customers/hooks/useQuickPay.ts), the same the phone list runs. While a row's pay or owed read runs, `DataTable`'s `rowBusy(row)` swaps its ⋮ for a small spinner. ## Navigation (was in Tech Stack)

> **Every tab stack under `app/(app)/(tabs)/` exports `unstable_settings = { anchor: "index" }`.** A web refresh (or any deep link) on a nested page rebuilds the navigation state from the URL alone, so without the anchor the tab's stack holds only that page — the tab icon's pop-to-top (`state.index > 0`) and `router.back()` both become no-ops. Keep it on **every** tab layout, including ones that have no sub-page yet. See gotcha #82.
>
> **The tab navigator sets `backBehavior="history"`.** React Navigation defaults to `firstRoute`, which sent Back from any tab root to the FIRST tab (Home) instead of the previously visited one — most visibly from Settings, which is still a tab (`href: null`) pushed from every screen's gear icon, and which under the default dropped a **non-admin** onto the admin-only dashboard (`href: null` hides a tab button, it does not remove the route). Stack pops still win, so Admin → Plans → Back is unchanged. See gotcha #93.
